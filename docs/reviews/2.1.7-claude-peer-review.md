# 2.1.7 · Claude Opus 5.5 공동 검토

2026-10-27. 사용자가 요청한 Claude Opus 5.5, high로 기존 Remote Control 세션에서 검토했다. 실제 응답의 model 필드와 CLI effort를 확인했다. 범위는 공개 2.1.6 소스 `874c7b1c`부터 공개 2.1.7 소스 `9aaabb80`까지의 변경과 직접 호출부다. Claude의 1차 보고 뒤 Codex가 소스·격리 재현·성능 측정으로 대조했고, 그 증거를 Claude가 재검토했다.

이번 작업은 리뷰와 수정·개선 제안을 정리하는 단계다. 제품 소스와 설치·공개 2.1.7(72)은 그대로이며 새 빌드·공증·릴리스·iCloud ZIP 전달은 하지 않았다. 사용자의 새 지시에 따라 앞으로 빌드 파일 전달은 GitHub/Homebrew를 사용한다. 앱의 iCloud 설정 동기화 기능과 기존 공유 파일은 보존한다.

## 결론

STP 본체 판별·실행 콜백 정정·첫 창 전환·Option 유지라는 주요 수정 경로를 깨는 새 중대 결함은 확인하지 못했다. 낮은 우선순위의 경계 동작 1건, 측정으로 뒷받침된 성능 개선 후보 1건, 실기 확인이 필요한 활성화 부작용 가설을 남겼다. 이는 모든 앱·Space·실패 조합의 안전을 입증한 결과는 아니다.

## 확인된 경계 동작: 메뉴바로 연 뒤 Option을 누른 경우

`main.swift:216`의 Space 변경과 `main.swift:902`의 최근 창 선택은 Option의 현재 눌림 상태만 검사한다. 메뉴바 → 열기로 연 패널은 `heldPresentation=false`이고 HoldMonitor의 `triggered=false`다. 이때 Option을 눌러 창을 선택하면 패널은 보존되지만, Option을 놓을 때 HoldMonitor는 onHide 대신 onAbandon을 호출한다. onAbandon과 onRelease의 실제 AppDelegate 연결에도 패널 닫기가 없어 고정하지 않은 패널이 남는다. Esc·바깥 클릭으로는 닫힌다.

Codex는 실제 HoldMonitor와 OverlayPresentation에 합성 이벤트를 전달하는 화면 없는 독립 실행으로 selection/Space 보존, release onHide=0·onAbandon=1·isPinned=false를 확인했다. 전역 모니터·앱 활성화·실제 창 표시는 하지 않았다. AppDelegate 판정식은 동일한 식을 옮겨 사용했으므로 픽셀 UI에서 직접 재현한 검증과 구별한다. Claude도 이 범위를 확인했다.

제안: 두 호출부의 `optionHeld`를 `heldPresentation && hold.optionDown`으로 제한하면 Option으로 연 패널의 보존과 해제 닫기를 유지하면서 수동으로 연 패널은 이전의 창 선택/Space 변경 닫기로 복귀한다. 수동으로 연 패널도 Option 모드로 승계하도록 만들려면 별도 UX 결정과 해제 수명 관리가 필요하다. 이 리뷰에서는 어느 동작도 새로 적용하지 않았다.

검증 권고: 수동/Option 호출 × 고정/미고정 × Option 눌림/해제의 실제 AppDelegate 결정과 HoldMonitor 연결을 함께 검사한다. 현재 테스트는 일반 정책과 앱 클릭을 검사하지만 이 조합은 빠져 있다.

## 성능 후보: 앱 식별자로 먼저 걸러내기

`ApplicationLaunchMonitor.swift:148`의 exact 검색은 matches를 호출하기 전에 각 프로세스의 번들·실행 파일 URL을 심볼릭 링크까지 정규화한다. 대상 bundleID가 알려진 경우 다른 ID를 먼저 제외해도 최종 matches 결과는 같다. ID가 nil일 때는 선필터를 생략해야 현재 의미가 보존된다.

권장 형태:

```swift
if let id = request.bundleID, app.bundleIdentifier != id { return false }
return request.identity.matches(/* 기존 경로·ID·실행 파일 대조 */)
```

Codex 2차 측정은 준비 실행을 버린 뒤 두 방법을 교차 순서로 각 40회 측정했다. 실행 프로세스는 157개였고 두 방법은 같은 STP 본체를 선택했다.

| 방법 | 평균 | 중앙값 | p95 |
|---|---:|---:|---:|
| 현재 exact 탐색 | 5.30ms | 5.22ms | 5.87ms |
| ID 선필터 후보 | 0.27ms | 0.26ms | 0.35ms |

이는 연결 대상이 아직 없을 때 수행하는 탐색 부분의 warm-cache 측정이다. 전체 앱 실행 시간·오버레이 프레임·cold cache 성능은 측정하지 않았다. 식별자 없는 기대값의 의미 보존은 코드 구조와 동일 선택 결과를 확인했으며 실제 nil-ID 앱을 실행한 검증은 아니다. 1차의 URL 단독 방식은 보조 프로세스에서 잘못 멈출 수 있어 정답을 유지하는 성능 기준으로 사용하지 않는다. 1차 max를 ‘첫 회 시간’으로 확정하지도 않는다.

함께 검토할 작은 정리: exact가 있으면 fallback 검색을 지연하고, 실행 요청이 없으면 confirmWindowReady의 추가 조회를 생략한다. 아직 제품에 적용하거나 개선 효과를 측정하지 않았다.

## 실기 가설: 런처 활성화와 다른 Space의 설정 창

AX 창이 없는 초기 복구에서 런처를 먼저 활성화한다. Option 없이 선택해 패널이 닫힌 상태이고 설정 창이 다른 Space에 열려 있으면, 설정 쪽 Space가 잠깐 보이거나 설정 창이 앞으로 나올 가능성을 Claude가 제안했다. 실패 시 런처가 활성 상태로 남을 가능성도 있다. 이번 검토에서는 실제 발생을 확인하지 않았다.

복구를 패널이 보일 때만 허용하는 완화는 Option 없는 전환의 개선 효과를 잃을 수 있다. 실기 증거 없이 적용하지 않는 것을 두 모델 모두 권한다. 확인할 때는 설정 창을 다른 Space에 둔 채 Safari/STP를 처음 열고 Option 없는 선택 및 앱 종료/복구 실패를 비교한다.

## 테스트와 진단 제거 대조
