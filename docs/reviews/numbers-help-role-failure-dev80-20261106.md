## 확인된 실패와 남은 불확실성

`MenuHelpDeferredResolver.swift`의 `copy`와 `role` 구현을 대조했다. 현재 roleReadFailure는 다음 분기를 합친다.

1. AXRole 읽기의 실제 API 오류(unsupported/noValue 제외).
2. success 응답이 nil 또는 문자열이 아님.
3. 문자열이지만 허용된 AXMenuBarItem / AXMenuItem / AXMenu 이외의 역할.

unsupported/noValue는 별도 roleUnavailable이므로 이번 기록과 다르다. 이번 실패는 2초 마감, 취소, 3,000노드/100자식/12깊이 한도 소진이 아니다. 500번째 방문 요소의 역할 처리에서 실패했지만 실제 역할명·오류 번호는 현재 로그로 확정할 수 없다. AXGroup, Services, custom view 등은 가설이며 원인으로 단정하지 않는다.

dev80의 children 세부 오류 필드가 없는 이유는 이번에는 children 읽기가 첫 실패가 아니기 때문이다. 앞서 방문한 모든 노드에서 children API를 호출했다는 뜻도 아니다(제외 루트/Help 경로 등은 건너뛸 수 있다). 회사 dev79의 43노드/109ms childrenReadFailure와는 다른 관측이며 두 부분 탐색의 시간을 성능 개선 수치로 비교하지 않는다.

## 추가 로컬 조회를 하지 않은 이유

임시 외부 검사 도구의 접근성 신뢰 검사만 수행했고 false였다. AX 조회는 0회, 권한 요청·변경은 0회였다. 외부 도구의 권한 결과를 Tile Launcher 자체의 권한 오류로 해석하지 않는다. CUA에는 이 목적의 메뉴 역할 한정 조회가 없어 Numbers 전체 UI/문서 조회도 하지 않았다.

## 다음 단계 제안 — 아직 구현·사용자 수락 전

실제 기존 Claude 세션과 Codex 독립 리뷰가 A(기존 읽기의 실패 분류)를 기본으로 하고 B(조건부 제한 구조 진단)를 함께 넣는 좁은 안에 동의했다. 최종 설계 방향에 차단 이견은 없다. 이는 에이전트의 제안 합의이며 사용자가 다음 구현 단계를 수락했다는 뜻은 아니다. A만으로는 미지원 역할 이름을 알아도 내부 구조를 몰라 다시 시험본을 만들 가능성이 남는다.

- A: 기존 AXRole 읽기의 실제 오류 번호 / nil·타입 범주 / SDK 역할 상수로 변환한 enum을 기록한다. 원본 임의 문자열은 기록하지 않는다. 실패 당시 root/depth/부모 맥락은 이미 알려진 정보가 있는 범위에서 구분하고, 없으면 미확인으로 둔다. 이를 얻으려고 새로운 부모 조회를 하지 않는다.
- B: 성공한 문자열이 SDK에서 알려진 미지원 역할일 때만 첫 실패 뒤 실행당 1회. API 오류·nil·비문자열·미지의 사용자 정의 문자열이면 실행하지 않는다.
- 기존 캡처는 먼저 incomplete로 끝낸다. 추가 관측 결과로 저장을 재개하거나 부분 목록의 유일성을 인정하지 않는다.
- 진단 빌드와 별도 실행 인자가 모두 켜진 경우에만 B를 허용한다. 일반 실행에는 추가 조회가 없다.
- 실패 요소 아래의 역할·자식 관계만 제한 조회한다. 형제는 이미 얻은 참조가 있을 때 같은 예산 내에서만 선택적으로 확인한다. AXParent·다른 루트·앱 전체/창 탐색을 추가하지 않는다.
- 상한: 총 64노드, 깊이 4, 자식 100, IPC 25ms, 별도 1초와 원 요청의 남은 마감 중 짧은 것. 매 호출 전후 취소/마감을 검사한다. 이는 협력적 제한이며 OS 호출의 실제 반환 시간을 엄밀히 보장하는 성능 수치가 아니다.
- 새 캡처/앱·프로세스·generation/설정 변경·stop 시 취소한다. 실패 요청 수명과 진단 취소 토큰을 분리하되 연결하고 정상 캡처가 진단을 기다리지 않게 한다. 구현 검토 때 실제 큐/실행 모델로 확인한다.
- 기록은 역할 enum·부모 인덱스·개수·오류·완료/잘림 사유뿐이다. 제목/Value/Description/Identifier/좌표/액션은 추가 조회·기록하지 않는다.
- “없음”은 허용 범위를 완전히 읽은 경우에만 표시한다. 미조회·미지원·오류·한도 도달은 unknown으로 남기며 부분 탐색을 완전한 구조로 오인하지 않는다.
- 기존 메뉴 조회 시간과 추가 진단 시간을 따로 기록한다. 추가 진단의 비용과 타이밍 영향이 있으므로 이전 dev80의 “추가 AX 조회 없음”과 구분해 안내한다.

검증 계획은 실제 읽기 helper에 공급자를 주입해 실패 분류·추가 조회 조건/0회 경로·한도/취소·원래 incomplete 및 저장 금지·출력 허용 필드·일반 빌드 제거를 확인하는 것이다. 알려지지 않은 역할을 무조건 container로 허용하거나 실패 가지를 생략하는 수정, 무제한 재시도, 단순 시간 확대는 선택하지 않았다. 관측 결과만으로 제품 정책을 자동 완화하지 않는다.

### 구현 단계에서 검증할 사항

Claude는 이미 읽은 부모 역할/자식 참조를 어댑터 내부의 제한된 맥락으로 보관하는 방안을 제안했다. 이는 새로운 AXParent 조회를 피할 수 있는 구현 후보이며 정확한 root/depth 복원·경로 보관의 상한·DFS 형제 이동 처리는 검증 전이다. 저장한 맥락으로 증명할 수 없으면 unknown으로 둔다. 관측 큐 완료 전달 전 원래 취소 토큰을 유지하며 진단하거나, 완료 후 별도 취소 토큰을 연결하는 구체 방식은 구현 때 실제 취소 흐름을 확인해 정한다. 어느 방식이든 새 요청이 이전 진단 전체 한도를 기다리도록 만들지 않는다. 25ms IPC 설정을 실제 선점/최대 대기 보장으로 표현하지 않는다.

## 현재 상태

재현 로그 확보와 실패 지점 분석은 완료했다. 지금 추가 사용자 클릭/파일 첨부/인증은 필요 없다. 다음 진단 구현·dev 제작은 사용자의 다음 단계 지시를 기다린다. Numbers 수집 문제는 아직 해결 완료가 아니다. 코드·버전·설치·Homebrew·정식 릴리스는 이번 분석에서 변경하지 않았다.
