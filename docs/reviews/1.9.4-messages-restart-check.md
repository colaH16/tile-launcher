# R231–R232 · 조회 정책 확인과 Messages 재시작 진단

2026-10-16. 사용자 질문을 변경 요청으로 잘못 받아들여 추가 확인을 했으나 사용자가 “바꾸라는게 아니라 질문”이라고 정정했다. **제품 소스/조회 횟수/배포본은 변경하지 않았다.** 현재는 앱 전환 때1회, 누적5회 실패 시 해당 실행 중 조회 중단이다. 앱 시작·표시 설정/권한 변경에 대한 기존 진입점과 성공 캐시도 그대로다.

## 요청·환경

사용자는 몇 번 창 전환 후 Messages 설정 타일이 나타났다며 여기 Mac에서도 Tile Launcher를 종료·재실행해 확인해달라고 요청했다.1.9.3에서도 재현된 문제이므로 설치본으로 확인해도 된다고 명시했다.

여기 설치/실행본은1.9.3(42)이었다. Messages는 실행 중이었으나 활성화 요청이 실패했다. 읽기 전용 세션 확인에서 frontmostBundle=com.apple.loginwindow, CGSSessionScreenIsLocked=1, 로그인 완료 상태를 확인했다. 잠금을 해제하거나 우회하지 않았다.

## 실제 수행

- 설치된 Tile Launcher1.9.3을 NSRunningApplication.terminate()로 정상 종료하고 같은 설치 경로에서 NSWorkspace로 백그라운드 재실행했다. 새 PID26793과 instance-owner의1.9.3/42/동일 지문을 확인했다. 강제 종료·설치 교체·설정 변경은 하지 않았다.
- 잠금 때문에 Messages를 활성 앱으로 만들지 못하므로 실제 오버레이에서 해당 타일의 표시 여부는 **검증하지 못했다**.1.9.4 trial 앱을 GUI로 실행한 비교도 하지 않았다.
- 별도 읽기 전용 진단에서1.9.3과배포1.9.4의실제find코드를추출해같은실행중Messages의메뉴메타데이터만각3회교차조회했다. 메뉴실행·대화선택·메시지본문/창제목읽기는하지않았다. AppItem/MenuCommand 등데이터형식은진단용최소형식을썼고find의AX읽기/판정코드는그대로다.

-1.9.4 코드: [2.101, 2.342, 2.027]ms,3회모두설정메뉴발견.
- 첫조회에서AXMenuBar43.137ms가가장느렸고전체46.464ms였다. 이후전체약2ms였다. 각조회속성47개중44개success/3개noValue로종료했으며오류/타임아웃예외는없었다.
- 이번직접조회에서는누락/타임아웃이재현되지않았다. 실제타일표시는잠금으로미확인이므로“재시작해도타일이잘나온다”라고결론내리지않는다.
- 사용자관찰은앞선실패가다음전환의조회로회복됐다는동작과맞지만그실패원인이타임아웃인지다른이유인지는구분할수없다. 이번성공값만으로집Mac의기존타임아웃가능성을배제하지않는다.

원시자료는/tmp/tile-r231-restart-locked.json,/tmp/tile-r231-menu-read.json,/tmp/tile-r231-session.swift의세션확인출력이다. 제품코드나공개자산을수정하지않았다.

## R233 · 사용자 추가 재현

오버레이를 연 채 Messages를⌘Q로 종료하고 다시 실행하면 설정 타일이 잡히지 않는다고 확인했다. 창 닫기가 아니다. 소스상 종료 시 PID 캐시는 초기화한다. didLaunch에서는 설정 탐지를 호출하지 않고 didActivate에서 호출한다. 따라서 새 프로세스의 didActivate/didLaunch 순서와 regular 판정, lastContext PID, 실제 read 시작 유무를 확인할 필요가 있다. 이 순서가 실제 원인이라는 관찰은 아직 없다.

find는 메뉴바나 후보를 받지 못하면 nil로 끝나며2초를 기다리며 재확인하지 않는다.2초는 전체 최대 예산이다. 메뉴 준비 전의 빈 응답도 타임아웃 없이 실패로 기록될 수 있으므로 실제 AX 상태/경과 시간과 함께 구분해야 한다. 제품 소스·조회 횟수는 변경하지 않았다.
