# R239 · 반복 AX 준비 시점 관찰 시험본

2026-10-16.1.9.4(47). build46 재발 뒤 사용자가 많은 반복 시도·API/오류 로그를 허용하고 먼저 언제 읽히기 시작하는지 조사하도록 요청했다. 앞서 승인한 일반 AX 오류2회 재시도는 이번 진단본에 적용하지 않는다. 실환경 재현은 사용자가 직접 수행하고 여기서는 합성 검증만 한다.

## 관찰 구조

--app-settings-probe가 명시된 세션만 AppSettingsProbe와32MiB Messages JSONL을 켠다. 기존 --app-settings-log는4MiB/반복 없음이다. 기본 실행은46의 제품 동작을 유지한다.

Probe는 앱이 시작 중이어도 활성화 시점부터 실제 ApplicationSettingsMenu.find를 읽는다. 동일 서비스 직렬 AX 큐를 공유해 제품 탐지/메뉴 실행과 동시에 호출하지 않는다. probe_queued와 실제 probe_read_start를 구별하며 각 요청은최대2초/개별읽기300ms다. 다음 시도는 완료 후0.2초이다. 실제 간격은 읽기시간+0.2초로,0.2초 정밀도의 OS 준비 시점 측정을 보장하지 않는다.

Probe 자체는 정상 미발견/읽기 오류를5회 이후에도 계속 확인하고, 연속3회 finder 성공 또는60초면 종료한다. 별도 만료 예약으로 응답이 아직 오지 않아도 세션/대기 요청을 취소한다. 전환/권한/종료/PID 시작시각 변경 때 취소하고 늦은 결과를 무시한다. 같은 완료 프로세스는 중복 활성화로 실험을 반복하지 않는다.

Probe 결과는 제품 지원 캐시/실패횟수에 반영하지 않는다. 따라서 probe 성공과 tileIncluded/제품 cache_published를 혼동하지 않는다. 정상 제품은 시작 완료/최대1초 대기 후1회와 실패5회 중단을 그대로 유지한다. 이 분리는 진단으로 읽힌 시점과 실제 제품 정책을 함께 비교하기 위함이다.

## API 기록

- component=settings/probe/menuCapture로 일반설정/실험/메뉴수집을 구별한다. probeID는관찰,requestID는개별읽기를 연결한다.
- 설정 finder: AXUIElementCreateApplication, AXUIElementSetMessagingTimeout, AXUIElementCopyAttributeValue(AXMenuBar/Children/Role/Title/단축키속성/Enabled 등 고정속성 이름), AXUIElementCopyActionNames의 코드·시작/끝 uptime·시간/예산.
- 메뉴수집: 연결 시도와 자체 지연 재시도, AX 속성 읽기/개수/목록/위치조회, AXObserverCreate, AXObserverAddNotification, CFRunLoopAddSource와 고정 메뉴알림. 기존 자동 수집이 꺼져 있으면 연결 API를 새로 호출하지 않고 probe_context.menuCaptureEnabled로 구별한다.
- 첫 AXMenuBar 읽기 성공과 전체 설정 후보/활성/AXPress 지원 확인 성공을 별개로 본다. 로컬 AX 객체 생성/timeout설정 성공만으로 원격 메뉴 준비를 판정하지 않는다. AXPress 실행은 하지 않는다.
- AX 값, 메뉴/창/대화/검색어/오류 설명, 다른 앱 식별 정보는 쓰지 않는다. 로그0600/O_EXCL/O_NOFOLLOW,32MiB 뒤 log_limit 후기록중단이다.

API 선후관계는 내부 준비의 원인을 입증하지 않는다. 반복 읽기 자체와 직렬 큐 대기가 타이밍에 영향을 줄 수 있어 실제 호출의 apiStartedMS/apiEndedMS와 큐 예약 시각을 구별한다.
