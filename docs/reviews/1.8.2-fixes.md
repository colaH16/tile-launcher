후속: 당시 미선택이던 리뷰2는 [R199·1.8.3](1.8.3-handoff-polling.md)에서 조회 완료 후0.4초 대기로 보완했다. 아래는1.8.2 당시 기록이다.

## 무엇이 잘못되어 있었나

저장 메뉴에는 원래부터 `File > Open`, `Project > Open` 같은 전체 경로가 있었다. 아이콘·고정 상태·기록도 MenuCommand UUID에 붙어 있었다. 문제는 별도의 번역표가 항목ID/전체 경로가 아닌 `Open`이라는 제목에 여러 메뉴의 번역 후보를 모았다는 점이다. 전체 경로가 서로 같다는 뜻도, 두 메뉴가 항상 하나로 합쳐진다는 뜻도 아니다. 잘못된 번역 후보를 허용할 수 있는 중간 자료 구조가 문제였다.

이제 아래처럼 항목을 분리한다. 표의 키는 설명용 예시다.

| 앱·리소스·상위 키·항목 키 | 영어 전체 경로 | 한국어 전체 경로 |
| --- | --- | --- |
| App / MainMenu.nib / file.title / document.open | File > Open | 파일 > 문서 열기 |
| App / MainMenu.nib / project.title / project.open | Project > Open | 프로젝트 > 프로젝트 열기 |

- NIB의 NSMenu/NSSubmenu 연결을 따라 전체 상위 경로를 만든다. 항목 식별에는 NSMenuItemIdentifier 또는 NSKey와 상위 항목의 키 체인을 사용한다. 리소스 파일 범위도 보존하며, 순환·여러 부모·중복 항목 키는 임의로 연결하지 않는다.
- 각 언어의 **완성된 전체 경로**를 보관한다. 한국어 상위 메뉴와 일본어 마지막 메뉴를 섞는 조합도 허용하지 않는다. 같은 번역 경로를 서로 다른 항목이 쓰면 그 경로를 자동 연결에서 제외한다.
- 원래 저장한 정확한 경로를 먼저 확인한다. 없을 때만 해당 항목의 확인된 다른 언어 경로를 독립적으로 찾는다. 읽기에 실패하거나 후보가 여러 개면 명령을 실행하지 않는다.
- 자기 앱 아이콘도 전체 경로로 연결한다. 다른 앱에서 가져올 때도 전체 경로가 같고 그림이 충돌하지 않는 경우만 쓴다. 아이콘 출처에는 항목 식별자·경로를 남긴다. 다른 앱의 그림을 쓰는 것과 그 앱의 실행 메뉴 ID를 공유하는 것은 별개다.

## 기존 사용자 데이터와 제외 목록

- 기존 MenuCommand UUID, 핀, 순서, 사용 기록, 직접 지정 심볼/아이콘 없음, 저장된 이미지 데이터는 유지한다. 기존의 제목별 pathAliases는 실행에 사용하지 않고 한 번 다시 확인한다.
- 새 메타데이터는 기존 `MenuIcons/v2` 이미지 폴더 아래 `apps-v3/<app hash>.json`에 저장한다. 구형 apps/*.json의 제목별 표와 분리해 잘못된 별칭을 다시 읽지 않으며, 기존 PNG/PDF 경로는 바꾸지 않는다. 아이콘의 앱 업데이트 자동 갱신 금지는 유지한다.
- 삭제 시 확인된 언어별 전체 경로를 기존 제외 목록에 모두 남긴다. 따라서 명령 객체를 지운 뒤에도 번역된 메뉴를 제외할 수 있다. 수동으로 다시 추가하면 확인된 경로를 함께 복원한다.
- 리소스를 읽는 동안 메뉴를 삭제한 경우도 완료 콜백이 메뉴를 되살리지 않고 확인된 제외 경로만 보완한다. 런처가 실행한 메뉴를 자동 수집에서 잠깐 억제할 때도 같은 전체 경로들을 사용한다.
- 과거에 이미 삭제해 식별/번역 정보를 잃은 항목까지 소급해서 복원할 수 있다고 보장하지 않는다. 새로 확인한 연결과 앞으로의 삭제에 적용한다.

**새 메뉴라고 모든 앱에서 불확실성이 사라지는 것은 아니다.** 앱이 정적 메뉴 리소스/식별 정보를 제공하지 않거나 메뉴를 동적으로 바꾸면 번역 연결을 확인하지 못할 수 있다. 그런 항목은 저장된 정확한 경로만 사용한다. 리소스의 NSKey와 런타임의 AXIdentifier를 같은 값으로 가정하지 않는다. 앱이 같은 경로를 다른 동작에 재사용하는 것까지 공개 정보 없이 증명할 수는 없다. 이번 수정은 동명 제목만으로 다른 항목의 번역·아이콘을 연결하던 경로를 제거한다.

## Handoff 표시와 메뉴 실행 대상

Handoff 타일은 여전히 Dock의 현재 Handoff 항목을 누른다. 왼쪽 메뉴의 이름과 앱도 바뀌지 않는다. 문제는 타일 표시에서 현재 문서A를 가린 뒤, 메뉴 실행 대상을 그 표시 목록에서 찾으면 같은 앱의B를 고를 수 있었다는 것이다.

`OverlaySnapshot.menuContextWindow`에 원래 목록의 현재 앱 창을 따로 보관한다. 표시용 Handoff 대체/개수 제한과 무관하게 왼쪽 메뉴는 그 창 ID를 사용한다. 해당 창이 닫히면 기존 focus 검증에서 실패하며, 클릭 처리에서 다른 문서로 임의 대체하지 않는다. 일반적인 활성 창 갱신은 새 현재 창을 반영한다.

## 조회 중단과 제한된 재시도

- WindowAttributeReader가 일괄 조회 실패, 일괄 결과 안의 AXError, 개별 속성 fallback의 통신 실패를 모두 구분한다. 첫 cannotComplete에서 그 앱의 남은 창/속성 조회를 멈춘다.
- 보존 중인 창의 최소화/유효성 조회에서도 통신 실패를 전파하며 이를 ‘닫힘’으로 취급하지 않는다. 창 없는 앱의 기존 항목도 읽기 실패만으로 지우지 않는다.
- 실패한 읽기는0.35초 뒤와 그다음1초 뒤에 최대2회 추가 시도한다. 재시도 사이에는 작업 큐를 점유하지 않는다. 성공/앱 종료/권한 해제 시 상태를 정리하고 사용자가 앱을 다시 활성화하면 새 예산으로 시작한다.
- 이 재시도는 창 정보 조회만 대상으로 한다. 메뉴 AXPress/Handoff 누르기를 자동 반복하지 않는다. Dock의 별도 polling 큐(리뷰2)는 이번 수정 대상이 아니다.

## Handoff 알림 실험

사용자가 다른 기기를 준비한 상태에서 각각60초씩 관찰했다. 첫 관찰은 항목 없음, 두 번째 관찰 시작에는Safari Technology Preview/iPad Pro M4 항목이 읽혔다. Dock이나 앱에누르기/키 입력을보내지않았다.

- Dock/목록/현재 Handoff 항목의 생성·삭제 알림 등록은 성공했다.
- 현재 Handoff 항목의 제목·값·레이아웃 변경 알림은 notificationUnsupported(-25207)였다.
- 두 번째60초 안에는 polling으로 확인한 항목 상태 변화도, 관련 알림 수신도 없었다. 따라서 전환을 알림으로 빠짐없이 감지할 수 있다는 결론을 내릴 수 없다.
-0.5초 확인과 클릭 시 현재 Dock 항목을 다시 찾는 동작을 유지한다. 사용자 결정대로 기기 변경을 추가 차단하거나 읽기 실패에 별도의 보존 유예를 추가하지 않는다.

로그: `/tmp/tile-handoff-review-probes/handoff-events.log`, `handoff-events-2.log`. 실제 앱/기기 전환이 관찰되는 다음 실험에서 생성·교체·종료 알림을 대조해야 알림 기반 조회 감소 여부를 결정할 수 있다.
