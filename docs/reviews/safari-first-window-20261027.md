# Safari 계열 첫 창 전환 · 2.1.7(68) 검증

## 사용자 재현 조건

Safari와 Safari Technology Preview를 완전히 종료한 뒤 실행하고, Option을 유지한 채 최근 창을 처음 선택하면 전환이 실패한다. 선택 직후 Option을 놓으면 전환되고, 창을 한 번 활성화한 다음에는 Option을 유지해도 정상이다. 다른 앱은 첫 선택부터 정상이라고 보고했다.

## 실제 관찰

읽기 전용 도구는 창 제목·내용·이미지를 수집하지 않고, 실행 상태·Option 상태·AX 반환 코드·창 ID·화면 표시 여부만 기록했다.

사용자 직접 재현의 STP PID 75492 표본 106개는 모두 `isFinishedLaunching=true`, `AXWindows=success(0)`였다. 실패 구간에는 AX 창 목록이 비어 있었다. 선택 직후 Option을 놓은 표본은 관찰 시작 후 50.940초, WindowServer 창 11420이 화면에 나타난 표본은 51.230초, 같은 ID의 AX 창을 얻은 표본은 51.523초였다. 이전에도 Option 해제 표본이 있었으므로, Option 해제 자체만으로 항상 전환된다는 뜻은 아니다.

따라서 이번 실패를 실행 완료 신호 누락이나 AX 오류로 설명할 수 없다. 제어 가능한 AX 창이 처음 노출되는 전환이 핵심이다. 다만 macOS/Safari 내부의 전환 보류 이유까지 확정한 것은 아니다.

## 제외한 후보

독립 도구에서 Option을 유지한 채 앱 열기를 한 번 요청했다. 122.528초 요청, 122.543초 같은 PID의 성공 콜백 뒤에도 AX 창은 비어 있었다. 두 번째 선택 무렵인 138.160초에 화면 표시, 138.449초에 AX 창 11628이 나타났다. 따라서 앱 열기 요청만으로 즉시 복구됐다고 해석하지 않았고 이 코드는 제품 후보에서 제거했다. 독립 도구와 실제 사용자 클릭의 활성화 문맥이 같다고도 가정하지 않는다.

## 68 후보의 변경

AX 창이 없는 첫 전환에서만 런처 활성화를 요청하고 최대 0.2초 동안 메인 런루프에서 확인한다. 이후 공개 `yieldActivation(to:)`와 `activate(from:options:)`로 대상 앱에 활성 상태를 넘기고, 원래 선택한 창 ID를 기존 상한 안에서 다시 조회한다. 대상이 종료되거나 다음 선택으로 취소되면 후속 동작을 중단한다. 창을 제어할 수 있는 기존 경로는 그대로다.

Option 키 합성·해제, 패널 닫기·자동 고정, 앱 재실행, Space 직접 쓰기를 추가하지 않는다. 실행 완료 판정 정책도 변경하지 않는다. 다른 창이나 다른 Space를 성공으로 간주하지 않는 기존 포커스 확인을 유지한다.

- 실제 Safari/STP 첫 선택의 개선 여부는 사용자 검증 중이다. 이 단계는 미공증 시험 설치이며 아직 정식 공개하지 않았다.

## 68 실기 결과와 69 보완

사용자는 첫 전환이 동작하지만 오버레이가 닫히고 등록 STP 타일에 로딩·클릭 차단이 남는다고 보고했다. 68 코드가 패널 닫기를 추가한 것은 아니지만, 실제 창 선택의 공통 처리와 Space 변경 알림의 기존 닫기 정책을 유지한다는 설명에서 이 부분을 빠뜨렸다. 이를 정정하고 사용자의 명시 선택을 반영했다.

68 관찰에서는 Option을 유지한 채 런처→STP 활성화 알림이 505.482/505.503초, 런처→Safari는 516.186/516.218초에 발생했다. 각각 506.021초에 AX 창12660, 516.705초에 AX 창12712가 관찰됐고, 사용자가 첫 선택 성공을 확인했다. 초기의 완료 값은 false였다가 이 전환 뒤 true가 됐다. 앞선 표본의 완료 값이 이미 true였던 경우와 함께, 플랫폼 완료 신호와 실제 창 준비가 항상 같은 시점이 아님을 보여준다.

69는 두 닫기 경로에서 Option 상태를 확인한다. 대상 앱의 데스크탑 전환을 막지 않고 오버레이만 유지하며, 고정 상태를 자동 변경하지 않는다. 해제와 Esc/닫기는 기존대로 작동한다.

등록 타일 대기는 정확한 창 포커스와 데스크탑 전환이 검증된 동일 생존 프로세스에 한해 해제한다. `windowReady`를 플랫폼의 `finished`와 별도 근거로 취급한다. 단순 경과 시간이나 메뉴 막대 활성화만으로 준비를 선언하지 않는다. 확인된 성공 뒤 도착한 실행 오류 콜백도 폐기한다. 원래 요청에 남은 대기의 내부 원인을 로그 없이 특정 캐시나 OS 알림 누락으로 단정하지 않는다.

합성 실행을 같은 실제 DeckView/NSHostingView에서 시작·해제한 검사는 모델 blocked=false가 된 뒤 타일의 action이 복원됨을 확인했다. 따라서 단순 UI 캐시 결함은 입증되지 않았다. XCTest295개/Python30개와 네이티브 요청/프로세스/늦은 콜백 보호·타일 갱신 검사가 통과했다. 임시 관찰 코드 및 새 네이티브 검사 분기는 Release 제품에서 제외된다. 69의 실제 오버레이 유지와 STP 로딩 해제는 사용자 실기 확인 대상이다.

69 소스 `fad7935c4de95473e5c908d6d30107ef9ad4188f`, 전체 tree `b93cb4516691203b0511dd0a25fc98cba3dd1ca6`의 격리 Release 빌드·Developer ID CloudKit 서명과 원본/ZIP 재추출 검증을 완료했다. 68을 정상 종료·백업하고 같은 사용자 경로에 69를 설치·실행해 PID/BuildID·최종번들해시 일치를 확인했다. 현재는 미공증 시험본이며, 배경 전환·오버레이 유지·STP 타일 대기 해제의 사용자 확인을 기다린다.


## 69 실기 재발 · 70 임시 진단

사용자가 오버레이 유지는 확인했지만 STP 최근 창 및 등록 앱 선택으로 전환하지 못하고 등록 타일의 로딩이 남는다고 보고했다. 따라서 69를 해결된 릴리스로 취급하지 않으며 공증/공개를 보류한다. 외부 로그의 STP PID81903은 약478.679초에 finished=true,490.795초에 창13301의 AX/화면 표시가 관찰됐으나 각 실제 클릭과 제품 결과를 연결하는 로그는 없으므로 성공으로 판정하지 않는다.

70은 전환/대기 정책 변경 없이 opt-in 임시 진단만 추가한다. 요청 ID와 PID, Option, 클릭 처리, 실행 요청/콜백/주기 조회, 보관된 앱 객체와 새 객체의 완료 상태, 활성화 요청/AX raise 반환 코드/정확한 창 확인 결과를 연결한다. 파일은 /tmp의 새0600 JSONL이고10분/4MiB로 제한한다. 창 제목·내용·메뉴·경로는 기록하지 않는다. 진단본은 정식 공증 전 제거한다.
