# R351 오버레이 커서 위치 계산 검토 · 2026-10-29

현재 상태: R351 분석 뒤 R352에서 Claude 선행 구현과 Codex 독립 검증·반복 상호 리뷰를 완료했다. 소스 수정과 검사 완료이며 설치·공증·공개는 이번 작업에 포함하지 않았다. 아래 R351 원인 분석의 행 번호와 미적용 표시는 수정 전 당시 기록이다. 사용자는 위아래 여백이 크게 남아 커서 위치에 오버레이가 나타나지 않는다고 보고하며 Claude와 함께 위치 계산을 검토해 달라고 요청했다. 현재 정식은 2.1.9(76)다.

## 결론과 원인

`PanelLayout.calculate`(Sources/DeckCore/Layout.swift:23–56)는 최대 높이의 창을 커서 중심에 배치하고 24pt 안전 영역 안으로 먼저 제한한다. `fittingContent`(:59–71)는 콘텐츠 높이로 창을 줄이면서 이미 제한된 큰 창의 중심을 유지한다. 따라서 실제 창이 더 작아도 최대 높이의 배치 제약이 남아 위아래 가장자리에서 불필요한 바깥 여백이 생긴다. 위아래 외부 여백 상수 24pt 자체를 크게 설정한 문제가 아니라, 최종 높이를 알기 전에 위치를 제한하는 순서가 핵심이다.

`buildOverlay` 비복원 분기는 등록 개수로 한 번, snapshot의 실제 workRows로 다시 fitting하며 두 단계 모두 큰 창 중심을 유지한다. `takePreparedOverlay`도 같은 식을 쓴다. 준비 시점의 옛 커서 좌표만 사용해서 생기는 문제는 아니다. 표시 시점의 최신 커서로 다시 계산하지만 같은 배치 순서 오류가 적용된다.

## 계산으로 확인한 반례

원본 DeckCore Swift 소스를 임시 실행 파일로 컴파일해 확인했다. 입력은 visibleFrame=(0,0,2560,1415), 배율1.4, 등록20개, workRows=3이다. 원본 최대 높이는1176pt, 최종 실제 높이는816pt로 나왔다. 최종 크기로 커서 중심에 다시 맞추는 제안의 결과와 비교했다. 좌표는 아래가0인 AppKit 좌표다.

| 커서 y | 현재 패널 y 범위 | 최종 크기로 위치 계산 | 불필요한 밀림 |
|---|---|---|---|
| 60 또는260 | 204…1020 | 24…840 | 180pt 위로 |
| 600 | 204…1020 | 192…1008 | 12pt 위로 |
| 707.5 | 299.5…1115.5 | 동일 | 0pt |
| 1100/1180/1350 | 395…1211 | 575…1391 | 180pt 아래로 |

가장자리에서 두 계산의 제한 조건이 모두 걸리는 구간의 차이는 (1176−816)/2=180pt다. 모든 커서에서 항상180pt라는 뜻은 아니며 중간에서는0…180pt로 달라진다.

영상은2560×1440이며6.5초의 패널 상단이 화면 위에서 약230px 떨어진 모습은 위 계산의229px(1440−1211)과 부합한다. 수정안에서는49px(1440−1391)이다. 영상의실제NSScreen.visibleFrame/배율값을직접수집한것은아니고메뉴막대25pt·1px=1pt라는가정이므로해당숫자는영상환경확정측정과구분한다. 원본기하함수의180pt편향재현자체는가정한입력에서확정됐다.

0.25초 표본에서도 초기 중앙 호출과 뒤쪽 위쪽 호출은 보이는 동안 대체로 같은 크기였다. 짧은 첫 프레임 내부 높이 변경까지 없다고 단정하지 않는다. 두 주요 호출 사이에 닫힌 구간이 수 초 있으므로 빠른 재열기 최대2초보다 긴 새 호출에서도 이 배치 문제가 드러난다. 영상의다른짧은재호출각각의키상태/설정값까지확인한것은아니다.

## 권장 수정안

1. 최종 콘텐츠 크기를 구한 뒤 `centered(on:visibleFrame:)` 같은 배치 전용 함수로 그 최종 프레임을 커서 중심에 놓고 동일한24pt 안전 영역에 제한한다. 크기·배율·타일 밀도는 바꾸지 않는다.
2. `buildOverlay`의 비복원 분기 마지막 fitting 뒤와 `takePreparedOverlay`의 마지막 fitting 뒤에만 적용한다. 새 호출과 Option 사전 준비 경로의 결과를 일치시킨다.
3. `refittingContent`는 기존 상단 고정 규칙을 보존한다. 빠른 재열기/실제 드래그 위치 복원/열린 상태의 프로필 및 내용 갱신을 새 커서 위치로 이동시키지 않는다.

화면 끝에서는 창 전체를 화면 안에 유지해야 하므로 커서가 항상 정확히 창 정중앙인 것은 불가능하다. 최종 실제 크기를 기준으로 가능한 한 커서 중심에 맞추고, 필요한 만큼만 경계 보정하는 것이 목표다. 실제화면이작아창폭이작업영역전체를쓰는경우가로위치자유도가없는것은이번세로여백문제와구분한다.

## 구현 시 필요한 검증

기존 검사는 화면 포함 여부·크기·프로필 상단 보존을 확인하지만, 들어갈 수 있는 최종 크기가 커서에서 불필요하게 떨어지지 않는지는 확인하지 않았다.

- 큰 화면 위/아래 및 중앙, 작은 노트북 화면, 음수 원점의 보조 모니터를 확인한다.
- 등록0/20/39개와 실제 workRows1/3/3.3을 조합해 화면 포함·최소 이동·크기/배율 불변을 확인한다.
- 최종 창이 커서 중심에 들어갈 공간이 있으면 중심이 커서와 일치해야 한다. 경계라면 최종 크기에 필요한 만큼만 이동해야 한다.
- 새 생성과 준비 재사용 두 호출처를 확인하고, 빠른 재열기/드래그/프로필 refitting의 기존 위치 규칙은 유지되는지 대조한다.
- 표시 뒤 늦은 앱/메뉴 정보로 높이가 바뀌는 경우는 상단 고정 정책에 따른 별도 현상으로 구분한다.

영상 프레임과 계산 원본, Claude의 독립 검토 원문은 ignored `docs/reviews/evidence/overlay-cursor-placement-20261029/`에 보존한다. 사용자의 개인 화면은 공개 문서에 넣지 않는다.


# R352 구현·성능·부작용 상호 검토 완료

사용자가 Claude 선행 구현 및 성능/부작용 반복 검토를 명시 승인했다. 기존 Opus5.5/high·Remote Control 세션이 제품 코드와 회귀 검사를 작성했고 Codex가 독립 검토·반례·실행 검사·성능 측정을 수행했다. 구현 전후 코드와 증거를 다시 Claude에게 보내 재검토하고, 성능 해석의 과도한 일반화까지 정정한 뒤 양쪽 모두 남은 제품 차단 이견이나 이번 범위의 미정 제품 선택이 없음을 확인했다. 모델 간 합의만으로 완료 처리하지 않고 아래 실행 결과를 근거로 했다.

## 실제 변경

- `Sources/DeckCore/Layout.swift`: 기존과 같은24pt 안전영역식을 `safeArea(in:)`으로 공통화하고, 크기/배율/compact/supported를 보존하면서 원점만 정하는 O(1) `centered(on:visibleFrame:)`을 추가했다. 같은 visibleFrame에서 계산·fitting한 크기를 받는 전제를 주석으로 명시했다.
- `Sources/TileLauncher/main.swift`: `buildOverlay` 비복원 분기의 **마지막** fitting 뒤와 `takePreparedOverlay`의 마지막 fitting 뒤에만 새 배치를 적용했다. 최초/준비 재사용 모두 최종 크기로 커서 중심을 맞추며, 화면 밖으로 나갈 부분만 기존 안전영역으로 제한한다.
- `Tests/DeckCoreTests/ScaledPanelLayoutTests.swift`: 가장자리180pt 반례, 화면6종/등록3종/행3종/커서7×7의2646조합, 재배치 후 refitting 위치/상단 보존의 세 검사를 추가했다.

추가 AX/Dock/화면 조회·타이머·폴링·캐시·새 컬렉션 저장소는 없다. 기존 전체 기하 계산 호출 횟수는 바꾸지 않고 값 타입의 고정 크기 배치 연산을 추가했다. 커서와 화면은 이미 각 호출처가 확보한 값을 쓴다.

## 반복 검토에서 다룬 사항

1. **첫 구현 대조:** 최종 fitting 뒤의 두 적용 위치와 복원 분기 제외를 확인했다. 기존 안전영역 공통화가 계산 결과를 바꾸지 않는지 별도 모듈 대조를 준비했다.
2. **입력 범위/부작용 재검토:** API의 동일화면·fitted크기 전제를 주석에 보완했다. 실제 두 호출처 모두 전제를 만족해 별도 축소/보호 분기나 상태를 추가하지 않았다.
3. **실행 결과 재대조:** 전체 검사, 변이 검증, 원본 대비 기하 출력, 새로운 두 경로의 최종 프레임, 성능 수치를 공유했고 차단 결함을 찾지 못했다.
4. **성능 해석 정정:** 캐시 예열된 microbenchmark를 실제 앱 비용의 상한으로 보거나, 전체 차이의 원인을 특정 init/복사로 확정하지 않기로 했다. 캐시가 절대 적중하지 않는다는 표현도 피하고, 작은 비용 대비 무효화 복잡성이 불필요하다는 판단으로 정리했다. 실제 화면의49px는 환경 가정값이며 실기 보장치로 안내하지 않는다. Claude도 모두 수락했다.

## 성능 측정

Apple M4, 물리/논리10코어, macOS27.2에서 Release `-O`, arm64/macOS26 target, DeckCore를 별도 모듈로 컴파일했다. 실행 시점 입력256개로 상수 접기를 방지하고 결과 합산값을 보존했다. 워밍업2만회 후 모드별20만회×13표본을 세 라운드에 걸쳐 실행 순서를 교대했다. 아래는 라운드 중앙값들의 중앙값이다. 함수 호출·합산 비용이 포함된다.

| 대상 | 기존 | 수정 후 |
|---|---:|---:|
| calculate + 최초 fitting + 최종 fitting (+새 배치) | 64.50ns | 77.58ns |
| 이미 fitted된 프레임 읽기 대조 / 새 배치 포함 | 3.60ns | 13.31ns |

전체 위치·크기 기하 계산은 약0.078µs=0.000078ms, 증가분은 약0.013µs=0.000013ms다. 전체 라운드 중앙값 범위는 기존64.16…65.18ns/수정75.71…77.75ns였다. 단독 배치 포함 측정은 첫 라운드19.85ns, 이후13.31/13.28ns였다. 이런 차이는 미세 측정의 실행 환경 영향을 보여 주므로 정밀한 실앱 지연 보장치로 쓰지 않는다.

이 수치는 해당 Mac의 예열된 기하 함수 microbenchmark이며 AX 조회·SwiftUI 구성·AppKit 창 표시를 포함한 오버레이 전체 열기 시간은 아니다. 원인을 고치기 위해 추가된 연산이 O(1)이고 이 조건에서 작게 측정됐다는 근거다. 입력이 달라질 수 있는 커서 위치를 별도로 캐시하거나 계산 구조를 크게 재편하는 최적화는 복잡성과 위치 무효화 위험에 비해 실익이 확인되지 않아 추가하지 않았다.

## 보존한 동작과 실기 범위

- 빠른 재열기와 실제 드래그 위치 복원은 기존 `refittingContent` 경로다. 새 커서로 강제 재중심하지 않는다.
- 보이는 창의 프로필/내용 갱신은 기존 상단 고정을 유지한다. 하단 안전 경계에 붙은 창의 내용이 커지면 화면 안에 들어오도록 위로 자랄 수 있다. 이는 기존 경계 보정 규칙의 결과이며 이번 수정이 새 정책을 추가한 것은 아니다.
- 폭이 안전영역 전체를 사용하는 화면에서는 가로 이동 여지가 없다. 타일 폭/배율/밀도를 바꿔 해결하는 범위로 확대하지 않았다.
- 같은 화면에서 fitting한 프레임만 새 배치 함수에 넣는다. 더 큰 화면에서 만든 임의 프레임의 재맞춤은 기존 refitting 경로의 역할이다.
- 실제 영상 환경의 최종 화면 확인은 새 시험본 적용 후 필요하다. 위·아래 가장자리 근처에서 새 호출이 커서를 포함하며 안전 경계 안에 열리는지 확인하면 된다.
