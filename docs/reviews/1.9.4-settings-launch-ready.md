# R237 · 시작 중 설정 탐지 실패 수정 시험본

2026-10-16. 개발1.9.4(46). 사용자가 수정·시험 전달을 요청했고 실기 검증 후 정식 재배포하기로 했다. 공증과 새 GitHub 공개/이 Mac 설치 교체는 하지 않는다.

## 근거와 범위

다른 쪽 에이전트는 권한 문제로 조작하지 못해 사용자가 직접 실환경을 재현했다. 사용자 제공 build45 로그 발췌 기준으로 최초 활성화는 finishedLaunching=false였고 AXMenuBar가 약2.25ms에 -25204를 반환했다. 이후 didLaunch에 추가 설정 조회가 없었고 다음 활성화의 두 번째 조회는 성공했다. 이 작업에서 삭제된 원본 로그를 복원하거나 읽은 것은 아니다. OS 내부 -25204 원인은 추정이며 timeout으로 단정하지 않는다.

## 수정

미발견 앱이 시작 중이면 바로 AX를 읽지 않고 프로세스 시작 시각을 포함한 대기 상태를 기억한다. 현재 대상과 같은 앱 ID/PID의 시작 완료 알림이 오면 한 번만 조회한다. 별도 앱의 didLaunch는 지원 탐지를 새로 시작하지 않는다. 성공 캐시는 시작 상태와 상관없이 바로 사용한다.

로컬 AppKit SDK NSRunningApplication.h는 일부 앱이 완료 알림을 보내지 않아 finishedLaunching이 계속 false일 수 있다고 명시한다. 따라서 최대1초 단발 대기 후 같은 최초 조회를 한 번 수행한다. 완료 알림과 단발 예약 중 먼저 실행한 쪽이 대기를 소비하고 나머지는 취소/무효화한다. 대기 중 새로 들어온 같은 활성화/권한/표시 갱신은 예약 시간을 연장하거나 추가 타이머를 만들지 않는다.

대기에는 실패 횟수를 부여하지 않는다. 완료된 읽기가 실패하면 기존처럼1회를 소비하고 다음 활성화까지 다시 읽지 않는다. 같은 활성화에서 연속5번 재시도하지 않는다. 실제 실패5회 중단·AX300ms/전체2초·성공 지원 유지·메뉴 실행 전 재탐색은 보존했다.

앱 전환·표시 끄기·취소·종료 때 예약을 지우며 실행 시에도 프로세스 시작 시각·현재 요청·권한을 재검사한다. 이전 취소 조회가 끝나기 전 완료 알림이 와도 기존 직렬 큐에서 새 조회 하나만 기다린다. 표시 갱신은 기존 onChange를 사용한다.

진단에는 launch_deferred/launch_ready와 origin launchCompletion/launchFallback을 추가했다. cache_published.reason도 실제 found/notFound/readerError를 유지해 정상 미발견과 AX 오류를 구별한다. 캐시 실패 횟수 계산에는 변화가 없다.

## 실기 확인과 한계

먼저 Tile Launcher를 완전히 종료해 성공 지원 캐시가 없는 상태에서 빌드46을 --app-settings-log로 실행한다. Messages ⌘Q/재실행 뒤 다른 앱을 거치지 않고 설정 타일이 나타나는지 확인한다. 로그의 launch_deferred→launch_ready→read_start와 성공 게시/타일 스냅샷을 함께 본다. 원래 요청처럼 여기 검사는 실제 집 Mac 재현 해결 확인을 대신하지 않는다.

시작 완료 알림은 AX 메뉴 준비까지 보장한다는 전제로 사용하지 않았다. 완료 뒤 또는1초 단발 조회에서도 AX가 실패하면 기존 정책상 다음 활성화까지 기다리므로, 그 경우 새 로그를 근거로 후속 조치를 정한다.1초 대기는 추가 읽기 예산이 아니며 오버레이 표시/UI를 막지 않는다.

빌드45는 진단과 성공 캐시 유지, 빌드46은 위 시작 대기 수정까지 포함한다. 기존 배포 ZIP은 보존한다. 전달본 서명/해시는 완료 후 아래에 기록한다.
