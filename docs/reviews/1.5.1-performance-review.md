# 1.5.1 성능 변경 리뷰 — R187

2026-10-15. 검토 기준은 `930b5cb6c5f2fc3a2380a6777da713a9bd82a762`이며, 이전 공개 상태 `18b62ff` 이후의1.5.0·1.5.1 변경을 읽었다. 사용자가 확인한 UI는 유지한다. 이 문서는 검토 결과이고 수정 적용이나 새 버전 배포가 아니다.

## 결과

조회 범위 축소, 정상 응답 앱의 AX 속성 일괄 읽기, 최근 창 스크롤 상태 분리는 타당하다. 기존 XCTest163개와 배포 검사23개도 통과했다. 다만 새 캐시 재사용과 단축키 갱신에서 각각 문제가 재현됐고, 응답하지 않는 앱에 대한 대기 제한은 아직 모든 조회 경로에 적용되지 않았다.

### [P2] 표시 직전 바뀐 창 목록·활성 앱을 준비된 화면이 반영하지 않음

위치: `Sources/TileLauncher/main.swift:328–342`, 특히329–336.

- Option 대기 중 준비한 화면을 꺼낼 때 권한, 프로필ID, 화면, 크기만 검사한다. 실제 창 목록, 현재 앱, 메뉴 목록의 변경 여부는 검사하지 않는다. 높이도 최신 목록이 아니라 준비된 snapshot의 workRows로 검증한다.
- 앱 실행/창 변경 직후 Option을 누르고, 지연된 AX 결과가0.25초 대기 중 도착하면 이미 닫힌 창이나 이전 순서가 표시될 수 있다. 입력 없이 활성 앱이 바뀌는 경우에는 이전 앱의 제목·메뉴까지 재사용한다.
- 격리 복사본에서 실제 buildOverlay/takePreparedOverlay를 사용했다. 준비 후 창 목록을 새 창 하나와 다른 앱으로 교체했는데 `accepted=true, staleIDs=true, cachedContext=preview.editor, currentContext=review.new-app`이었다. 창은 화면에 표시하지 않았다.
- 권장: 창/컨텍스트/메뉴 데이터 revision을 준비 결과에 기록하고 표시 직전에 대조한다. 바뀌었다면 준비한 패널의 내용을 새 snapshot으로 갱신하고 크기를 재검증하거나 폐기해 다시 만든다. 화면에 표시한 이후의 번호/순서 동결은 유지한다.

### [P2] 개별 창 조회 실패에서는 반복 대기가 남고 호환 경로는 더 많은 요청을 보냄

위치: `Sources/TileLauncher/WindowTracker.swift:209–218, 290–304, 333–345`.

- 앱의 AXWindows 목록 자체가 `.cannotComplete`를 반환하면 기존 창에 재조회하지 않는 개선은 동작한다.
- 목록은 성공했지만 창 속성 일괄 조회가 실패하면 unresponsive가false다. 각 창에 계속 일괄 조회를 시도한 다음, 누락 보존 루프에서 minimized와role을 다시 읽는다.
- 일괄 조회가 `.notImplemented`인 호환 경로는6개 속성을 모두 개별 조회한다. 첫 역할 조회부터 실패해도 중단하지 않아, 이전 방식의 role/subrole 확인보다 실패 시 비용이 커질 수 있다.
- 실제 WindowTracker 코드에 가짜 AX 응답만 주입한10창 검사:

| 가짜 응답 | 배치 요청 | 개별 타임아웃 반환 | 기존 창 유지 |
| --- | ---: | ---: | ---: |
| 앱 목록 자체 실패 | 0 | 1 | 10 |
| 목록 성공, 각 창 배치 실패 | 10 | 20 | 10 |
| 목록 성공, 배치 미지원, 개별 읽기 실패 | 10 | 80 | 10 |

이 검사는 요청 횟수 재현이며 OS가 실제로4.5초/12초 멈췄다는 측정은 아니다. 현재 설정된0.15초를 각 실패가 모두 소진한다면 두 번째는30회×0.15초, 세 번째는80회×0.15초의 대기 가능성이 있다. 조회와 창 선택이 같은 직렬 큐를 쓰므로 선택 처리도 뒤로 밀릴 수 있다.

권장: 개별 창에서 처음 `.cannotComplete`가 나오는 경우도 해당 앱의 이번 갱신을 중단하거나 제한된 예산을 사용한다. 이미 실패한 창에는 유지 판정용 재조회도 하지 않고 알려진 값을 보존한다. 호환 경로는 role/subrole 검사를 먼저 하고 실패하면 나머지를 읽지 않는다. 실제 닫힘/최소화/숨김 보존 규칙은 별도로 유지한다.

AX의 배치/개별 오류와 메시징 실패 구분은 [Apple의 AXUIElementCopyMultipleAttributeValues 문서](https://developer.apple.com/documentation/applicationservices/1462051-axuielementcopymultipleattribute) 및 [AXUIElement 헤더 설명](https://developer.apple.com/documentation/applicationservices/axuielement_h)과 대조했다.

### [P2] 메뉴에서 없어진 단축키가 자동 수집 후에도 남음

위치: `Sources/DeckCore/MenuCapture.swift:103–106`.

- 기존 메뉴는 새 단축키가있을 때만 저장한다. 단축키가 사라져 새 값이nil이면 이전 값을 지우지 않는다.
- 기존⌘K가 저장된 사용자 메뉴를 단축키 없는 메뉴로 다시 수집하는 순수 정책 호출에서 `before=⌘K, after=⌘K`가 재현됐다. 아이콘이 없는 메뉴 타일은 오래된 단축키를 계속 표시한다.
- `SettingsStore.updateShortcut`을 사용하는 런처 직접 실행 경로는nil을 지우지만, 실제 앱 메뉴에서 선택해 자동 수집하는 경로에는 이 처리가 없다.
- 권장: 단축키 없음이 확인된 경우 기존 값도nil로 갱신한다. AX 읽기 실패와 확정된 없음은 구분해 일시적인 읽기 실패 때문에 정상 값을 지우지 않게 한다. 사용자가 확인한 아이콘 우선순위/타일 UI는 바꿀 필요가 없다.

## 실제 측정한 개선

개발 Mac에서 창을 조작하지 않고 읽기 전용 WindowServer 메타데이터 갱신을 측정했다. 과거 DesktopWindows 코드와 현재 코드를 같은 프로세스에 넣고 각5회 예열+30회 실행의 중앙값을 사용했다. 양쪽 기록 수는223개였다.

| 범위 | 이전 | 현재 |
| --- | ---: | ---: |
| WindowServer 목록/정렬 메타데이터 갱신 | 8.364ms | 5.173ms |

현재 입력은 실행 중인 일반 앱 PID 집합이며 AX에서 이미 알고 있는 창ID는 비어 있는 조건이다. 실제 앱의 유지 중인 AX 캐시까지 동일하게 복원한 실험은 아니며, 전체 오버레이가38% 빨라졌다는 뜻도 아니다. 조회 범위를 줄인 변경이 이 단계의 비용을 낮춘 근거로만 사용한다.

## 추가 성능 개선 후보

`WindowTracker.swift:358`은 한 앱의 창을 처리할 때도 서버의 모든 창을 먼저 정렬한다.368행에서는 같은 전체 목록을 다시 필터링한다. 먼저 해당PID의 목록을 한 번 만든 뒤 그것만 정렬하고 개수를 재사용하면 결과 순서를 그대로 유지하면서 비용을 줄일 수 있다. 이벤트를 합치거나 MRU 갱신 횟수를 줄이는 변경은 필요 없다.

같은 합성 입력/결과 checksum, `swiftc -O`,10회 예열 후5배치 중앙값으로 이 CPU 처리 부분만 비교했다:

| 입력 | 현재 전체 정렬 | PID 필터 후 정렬 | 전체 PID 색인 생성 포함 |
| --- | ---: | ---: | ---: |
| 서버 기록237개·앱1개 갱신 | 0.00638ms | 0.00061ms | 0.01265ms |
| 서버 기록237개·앱30개 갱신 | 0.18669ms | 0.02523ms | 0.02285ms |
| 서버 기록2000개·앱80개 갱신 | 15.71194ms | 0.31504ms | 0.12878ms |

작은 단일 앱 갱신에서는 전체 색인을 매번 만들면 오히려 비싸다. 우선 단순한 ‘필터 먼저’ 방식이 적합하다. 큰 목록에서만 갱신당 한 번 만든 PID 색인을 공유하는 방식을 추가 검토할 수 있다. 이 수치는 AX/WindowServer/화면 렌더 비용을 포함하지 않으며, 보통 목록의 절대 절감량은 작아서 위의 실패 경로/캐시 일관성 수정이 우선이다.
