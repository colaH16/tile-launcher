# 1.8.1 Handoff·언어별 메뉴 코드 리뷰

2026-10-15. 기준 `d34e962c32bdef45833157400fa3e8f9aa06898c`, 제품1.8.1(36). 비교 범위는5fbdda7 이후의 메뉴 언어 지원·AX 보완·Handoff·갱신 통일·모양 설정이다. 사용자가 개선 후보와 부작용/추천도/위험도를 먼저 검토한 뒤 함께 결정하자고 했으므로 **제품 수정·버전 변경·설치·배포는 하지 않는다.** handoff.md는 사용자가 파일명을 잘못 본 것으로 정정했고 README·AGENTS·CHANGELOG·요청 기록을 기준으로 검토했다.

## API 질문에 대한 정확한 답

공식 Handoff API는 있다. `NSUserActivity`와 앱 delegate의 이어받기 메서드는 앱이 자기 활동을 전송·복원하는 용도다. 공개 문서/설치 SDK에서 **Tile Launcher가 Dock에 현재 뜬 Safari·메모·음악 등의 Handoff 제안을 직접 조회·실행하는 전용 API는 확인하지 못했다.** 자기 앱의 Handoff 구현과 Dock의 다른 앱 제안을 대신 표시하는 기능은 구분해야 한다.

- [Apple: Implementing Handoff in Your App](https://developer.apple.com/documentation/foundation/implementing-handoff-in-your-app)
- [Apple: Continuing User Activities with Handoff](https://developer.apple.com/documentation/foundation/continuing-user-activities-with-handoff)

“여러 앱의 Handoff를 한꺼번에 읽는다”는 앞선 설명은 오해 소지가 있어 정정했다. API로 여러 제안을 받을 수 있다는 뜻이 아니다. 현재 코드는 **Dock 프로세스의 자식 아이콘들을 역순으로 확인해 `AXHandoffDockItem` 하나를 찾는다.** 찾으면 멈추고, 없으면 일반 Dock 아이콘들의 종류까지 확인한다. Safari·메모·음악 앱 각각에 Handoff 질의를 보내는 방식이 아니다. 배지 이미지를 인식하는 것도 아니다.

Dock AX는 현재 실용적인 경로지만 “유일하게 가능한 모든 기술적 방법”이라고 단정할 수는 없다. 또한 Dock AX 사용이 곧0.5초 주기 확인의 필수성을 뜻하지 않는다. 비공개 Dock subrole과 구조에 대한 의존성은 남는다.

## 현재 구현에서 잘 된 부분

- 0.5초 확인은 오버레이가 보이는 동안에만 한다. 숨길 때 Timer를 해제하고, Option 준비 때 한 번 미리 읽는다. 하루 종일 모든 앱을 순회하는 모니터가 아니다.
- AX 읽기는 메인 스레드 밖에서 하고, Handoff 모델이 바뀔 때만 화면 갱신을 요청한다. 클릭 때 다시 Dock 항목을 찾는 것도 올바른 기본 방향이다.
- 사용자가 확정한 Option 유지/고정 갱신 통일,0.25초 준비 화면, 첫 타일 대체 정책을 이번 리뷰를 이유로 되돌리지 않는다.
- 모양 설정은 메뉴 → 최근 창 → Handoff → 등록 항목이며 기존 색 저장과 호환된다. 기본580×918pt 콘텐츠 크기의 비표시 네이티브 렌더에서 전체 설명과 초기화 버튼까지 보였다. 이번 섹션 추가 때문에 기본 크기가 잘리는 문제는 관찰하지 않았다.

## 실제 측정과 재현 범위

### 읽기 전용 Dock 확인

이 Mac(macOS27.2 베타)의 Dock47개 항목을20회 읽었다. 평균0.977ms, 최대1.335ms. 당시 Handoff 제안은 없었다. 정상 상태 조회의 벽시계 시간이며 CPU/배터리/사용자 체감 지연 측정은 아니다. 프로브는 각 요소에 짧은 시간 제한을 설정했고 실제 Dock에는 AXPress를 보내지 않았다.

AXObserver 등록 결과는 다음과 같다. root와 목록 요소 모두 같았다.

| 알림 | 등록 결과 |
| --- | --- |
| AXCreated / AXUIElementDestroyed / AXSelectedChildrenChanged | success(0) |
| AXLayoutChanged / AXTitleChanged / AXValueChanged | notificationUnsupported(-25207) |

등록 성공만으로 Handoff 생성·교체·종료 때 알림이 빠짐없이 온다고 볼 수 없다. 이번5초 관찰에서는 실제 Handoff 전환을 일으키지 않았다. **현재0.5초를 무작정 줄이거나 알림만으로 대체할 근거는 없다.** 알림+보완 주기 확인은 다음 실험 후보이다.

- [Apple: AXObserverAddNotification](https://developer.apple.com/documentation/applicationservices/1462089-axobserveraddnotification)
- [Apple: AXUIElementSetMessagingTimeout](https://developer.apple.com/documentation/applicationservices/1459345-axuielementsetmessagingtimeout): 특정 요소에 설정한 시간 제한은 다른 요소로 상속되지 않는다. 현재 Dock 코드의0.3초는 최상위 앱 요소에만 걸려 있다.

### 합성 재현

실제 앱의 창/메뉴/기기 작업을 실행하지 않았다. 생산 코드를 임시 복사본에서 사용하거나 AX 입출력 경계만 모의 함수로 바꿨다.

1. 현재 문서A와 같은 앱의 이전 문서B를 두고 Handoff가A의 타일을 대체하면, 메뉴 버튼의 `snapshot.windows.first { pid == context.pid }` 결과가B로 바뀌었다. 실제 메뉴 실행 경로는 그 창을 focus한 뒤 명령을 실행한다. 같은 입력에서B가 대표색으로 바뀌는 것도 확인했다.
2. Dock 읽기를0.8초로 모의하고0.5초 간격으로6회 요청했다.3초 뒤 주기 요청을 멈췄을 때4개가 시작되고3개가 끝났다. 그 뒤 클릭 요청은 약2.48초를 기다렸다. 실제 Dock 지연을 측정한 것이 아니라 **현재 serial queue가 읽기 요청을 합치지 않는 결과**를 재현한 것이다.
3. 화면에 표시한 항목은ReviewApp/iPhone, 새로 읽은 항목은ReviewApp/iPad로 주었다. 현재 `press`의 제목 비교를 통과해 모의 AXPress가1회 호출됐다. 실제 Dock은 누르지 않았다.
4. 서로 다른 리소스 키document.open/project.open의 영어 제목을둘 다Open, 한국어를문서 열기/프로젝트 열기로 주었다. 저장한File→Open의 별칭에 두 한국어 제목이 함께 들어갔고File→프로젝트 열기를 받아들였다. 이는 가상 입력이며 특정 실앱에서 오실행을 관찰한 것은 아니다.
5. File→Open을 수집 제외한 뒤 같은 동작의 한국어파일→열기를 넣으면 수집 허용 결과가true였다. 제외 목록은 아직 정확한 표시 경로만 비교한다.
6. 창 속성 일괄 조회가미지원, 역할 조회는성공, 나머지5개 속성은시간 초과인 입력을3창에 주었다. batch3회+role3회+실패 속성15회를 읽고 앱 무응답으로 인식한 횟수는0이었다. R191은 batch/role 단계 실패는 줄였지만 이후 개별 속성 실패까지 전파하지 못한다.

## 메뉴 식별자 질문 정리

사용자는 “내부 식별자마다 아이콘과 고정 여부를 저장하면 되지 않나”라고 제안했다. 방향은 맞다. 현재도 저장된MenuCommand UUID에 아이콘·핀·사용 기록을 붙인다. 결함은 **언어가 바뀐 외부 메뉴를 그 UUID에 연결할 때 이름 중심 번역 표를 쓰는 것**이다. 설명의document.open/project.open은 합성 입력의 예시 키이며 실제 앱들이 공통으로 제공하는 공개ID가 아니다. 리소스의NSKey와 런타임AXIdentifier를 동일하다고 가정하지 않는다. 기존 사용자 데이터는 유지하고 리소스 단위 식별·경로 확인만 강화하는 방향을 제안했다. 아직 구현 결정/수정은 하지 않았다.

두 번역 후보가 실제 부모 메뉴 아래 함께 있으면 현재 코드도 여러 개라며 멈춘다. 잘못된 번역 후보만 하나 존재할 때 오인할 수 있다는 것이 재현의 의미이며, 두 메뉴가 항상 하나로 합쳐진다고 표현하지 않는다.
