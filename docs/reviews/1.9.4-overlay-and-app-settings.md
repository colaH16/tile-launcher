# 1.9.4(43) 오버레이·앱 설정 수정 검토

2026-10-16. 공개/설치본은1.9.3(42). 이 문서는 개발 소스 검증이며 새 공증·GitHub 릴리스·설치를 뜻하지 않는다.

## 변경과 근거

- **배경 드래그**: 기존 상단 전용 영역을 전체 패널로 넓혔다. 현재 창의 leftMouseDown만 로컬 모니터로 읽고 타일/버튼/프로필/폴더 컨트롤과 NSScroller는 원래 이벤트를 돌려준다. DragView 자체 hitTest는 nil이며 휠을 구독하지 않는다. 스크롤 밖 타일 anchor가 헤더/하단을 덮지 않도록 각 viewport로 교차한다. 크기·간격·배율은 변경하지 않았다.
- **연속 앱 종료**: 창 없는 앱의 종료 요청에서만 오버레이를 고정한다. Option 해제/외부 클릭으로 닫히지 않아 연속 종료가 가능하고 Esc/닫기는 유지한다. 기존 정상 terminate 요청을 사용하고 강제 종료하지 않는다. 실제 사용자 앱 종료 없이 주입한 종료 요청으로 검사했다.
- **설정 탐지**: 오버레이를 여는 시점의 조회를 없애고 시작 시 현재 앱과 활성 앱 전환 때 확인한다. PID+시작 시각별 성공/실패 횟수/중단 상태를 메모리 캐시한다. 처음 포함5회 실패 또는 성공이면 이후 조회·횟수 갱신을 중단한다. 앱 종료·재실행 또는 런처 재시작으로 초기화된다. 취소/대상 전환의 늦은 결과는 실패 횟수에도 넣지 않는다. 단일 작업자와 최신 요청 하나만 유지한다.
- **읽기 제한**: 사용자 최종 요청에 따라 개별 AX300ms/조회 전체2초다. 대기열 대기는 새 앱의 응답 예산에 넣지 않는다. 처음 제안한0.20초 반복 재시도는 폐기했다. 실제 메뉴 실행 전에는 항목을 다시 찾고 AXPress 전에 읽기 제한을 해제한다.

Messages는 사용자 build42에서 표시 옵션이 켜진 상태에서도 일시 누락됐다가 다시 나타났다. 이 Mac의 읽기 전용 AX 진단에서는 앱 메뉴 Settings…/⌘,/활성/AXPress가 확인됐고 기존 실제 finder도 첫34.5ms, 이후 약2ms로 성공했다. 따라서 타임아웃은 가능한 원인 중 하나이며 확정 재현으로 기록하지 않는다. 앱이 설정을 늦게 제공해5회 모두 실패하면 같은 실행 중에는 계속 숨겨진다. 이것은 사용자가 선택한 조회 중단 정책이며 앱 재실행으로 재확인한다.

## 검증

- XCTest215개, 배포 스크립트 Python23개 통과. 스크롤 밖 타일/중첩 viewport의 드래그 제외 검사2개를 추가했다.
- Release 앱 빌드 통과. 실제 빌드의 비표시 AppKit fixture에서 성공 캐시, 실패5회 중단과 추가 변경 콜백 없음,3번째 활성화에서 복구, PID 재사용/종료, 늦은 결과 취소를 확인했다.
- 비표시1568×869/배율1.4 패널에서44개 타일/컨트롤 제외, 헤더/측면/하단 드래그 분기, 오른쪽 클릭 통과, 비활성 해제를 확인했다. performDrag만 검사용 콜백으로 대체했으므로 실제 마우스로 창이 움직이는 실기는 별도다.
- 실제 AppDelegate 실행 경로에서 두 번 연속 종료 요청, 숫자 대기 취소, Option 해제/포커스 변화에 대한 유지 정책과 Esc 닫힘을 검사했다. 일반 클릭·숫자 실행 검사도 통과했다.
-39개 등록 타일을2560×1056,1440×876,1280×776,1024×744 작업 영역에서 렌더했고 common-app-settings.png의 제목·설정 타일·등록3행을 육안 확인했다.
- 전체 비표시 렌더 exit0. 기존 macOS27.2 beta NSTableView reentrant 경고3건은 계속 발생했으며 이번 수정의 실패로 숨기지 않는다. 실제 사용자 전경 앱/메시지/창은 조작하지 않았다.

## R225 · 추가 사전 로드 검토 (제안, 미구현)

최근 창은 사용자 결정대로 추가 조회/사전 로드 대상에서 제외한다. 빈번한 전환마다 새 작업을 만드는 것이 총 CPU를 줄인다는 가정도 하지 않는다.

| 후보 | 현재 코드 | 적합한 갱신 시점·주의점 |
|---|---|---|
| 앱 아이콘 | AppIconCache가 경로별 NSImage를 최대96개 캐시, 첫 렌더에서 로드 | 처음 활성화한 앱의 캐시가 없을 때만 준비 가능. 오버레이에 안 나올 앱까지 읽으면 총 작업·메모리는 오히려 늘 수 있어 측정 후 판단 |
| 저장 메뉴 이미지 | 리소스 추출은 이미 utility queue, 카탈로그는 디스크 보존. SavedMenuImages는 최대512개/누락도 캐시 | 현재 앱의 저장된 PDF/비트맵/Symbol을 처음 표시하기 전 준비 가능. 리소스 재스캔 없이 준비하고 수동 아이콘 변경/새로고침 때 무효화 |
| 메뉴 표시 목록·정렬 | snapshot 갱신 때 ordered/frequentIDs 계산 | 앱 전환보다 메뉴 수집·사용 기록·핀·아이콘·기간 변경 때 갱신이 적합. 최근/자주 사용 기간 만료는 별도 고려. 계산 자체가 가벼울 수 있어 프로파일 전 우선순위 낮음 |
| 등록 앱의 현재 경로 | PinnedItem.url에서 Bundle ID 경로 조회 | 등록 목록 변경 때 준비 가능. 앱 이동/삭제/업데이트 시 stale 경로 주의. 실행 시 재확인 필요 |

권고는 아이콘 첫 읽기 지연을 측정한 뒤 실제 체감이 있으면 캐시가 비었을 때만 준비하는 것이다. 사전 로드는 비용 시점을 앞당기는 작업으로 총 CPU 감소와 다르다. 메뉴 수집용 AX 관찰자는 이미 활성 앱 변경에 맞춰 전환되고 있으므로 전체 메뉴 트리를 더 자주 읽는 제안은 하지 않는다. 오버레이 패널 자체는 이미 Option0.25초 대기 중 준비한다.

## R229 후속 선택

사용자가 사전 측정 후 아이콘 읽기만 승인해 앱/저장 메뉴 이미지의 사전 읽기를 같은1.9.4 소스에 추가했다. 위 R225 표의 제안 상태는 당시 기록이며, 현재 구현 범위·검증은 [아이콘 사전 읽기](1.9.4-icon-read-ahead.md)에 정리했다. 메뉴 정렬 캐시·사전 그리기는 적용하지 않았다.
