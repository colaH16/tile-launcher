# 현재 요구사항

최종 기록일: 2026-10-12 (Asia/Seoul)

현재 작업 범위: **R23에 따라 첫 네이티브 개인용 빌드를 구현 중**. 제품 표시 이름은 **Tile Launcher**. R30에서 사용자가 제공한 `colaH16/tile-launcher`에 커밋·푸시를 승인했으며 기존 MIT 라이선스와 이력을 보존함. Sites 게시·App Store·Homebrew 배포는 중단 상태임.

## 첫 빌드 기준 — 이전 검토안보다 우선

- R37 디자인 원칙: **큼직한 타일과 터치용 UI처럼 넓은 클릭 영역을 유지하는 macOS 앱**. 버튼 크기·여백의 선호와 플랫폼의 시각/조작 관례를 구분하며, 큰 타일과 macOS 기본 UI/UX를 함께 만족시킴. 새로운 크기 수치를 지정한 요청은 아님.
- R39: 오버레이가 열린 뒤에는 Command 등 보조키 추가만으로 닫지 않음. Option을 계속 누른 채 `⌘,`로 설정을 즉시 열 수 있으며 고정을 먼저 요구하지 않음. 오버레이가 키 입력을 받을 때만 로컬 처리하고 원래 앱에는 중복 전달하지 않음.
- R39: 사용자는 Space가 ChatGPT와 겹친다며 왼손의 `⌥X` 또는 `⌥A`를 제안함. 에이전트가 두 후보 중 **`⌥X`로 고정**을 초기 기본값으로 선택함. 누르고 있던 Option에 X만 추가하며 반복 입력은 무시. 닫기는 Esc/`⌘W`/`×`, 다음 호출은 고정 해제. Space·A를 새로 점유하지 않음.
- R32: 기존 헤더 버튼 하나를 핀 → 닫기 `×`로 전환. 고정하면 Option 해제·조합키·바깥 클릭으로 닫히지 않으며 캡처 도구를 사용할 수 있음. `×`/Esc로 닫으면 다음 호출은 일반 모드. 고정 중 앱·파일 실행은 창을 유지하고 Option이 눌렸다면 해제까지 실행을 보류함. 설정/권한 화면 이동·디스플레이 구성 변경은 닫음. 이 세부 수명 정책은 초기 구현 기본값임.
- R33: 설정에서 Dock의 고정 앱·폴더를 원클릭으로 가져옴. Finder → 고정 앱 → 폴더 → 통합 휴지통 순서. 기존 중복 항목은 이름/모드를 유지하여 Dock 순서로 배치하고 Dock 밖 기존 항목은 뒤에 보존함. 비고정 실행 앱·최근 앱·최소화 창·링크·개별 문서는 가져오지 않음. 읽기 실패/지원 불가 항목을 알리고 Dock 자체는 변경하지 않음.
- R34–R36: 창 고정/닫기는 **왼쪽 위**, 앱 이름·관찰된 해당 앱의 최근 창 제목(없으면 설명)은 **중앙**, 현재 프로필과 설정은 **오른쪽의 하나의 유리 캡슐**에 배치. 제목 중앙은 좌우 컨트롤 너비와 독립적으로 유지함. 폴더 진입 시에도 같은 구조에서 중앙 제목만 바뀌고 뒤로 가기는 왼쪽. 집중 모드 기능 자체는 여전히 다음 단계임.
- 앱이 키 입력을 받는 상태에서는 AppKit 메뉴의 `⌘W` 닫기, `⌘,` 설정, `⌘H` 가리기, `⌘Q` 종료를 제공. 다른 앱의 단축키를 전역으로 가로채지 않음.
- 사용자 선택: Option 호출·최근 앱·최근 창·수동 등록 항목을 먼저 구현. **행 우선 + 세로 스크롤, 커서 중심 + 화면 경계 보정**을 채택함. 이후 문단의 ‘선택 미정’은 과거 검토 상태임.
- 추가 요청: 등록 항목은 앱과 폴더를 포함. 일반 폴더는 항목별로 ‘오버레이에서 탐색’ 또는 ‘Finder에서 열기’를 선택·저장. 오버레이의 파일·앱은 기본 연결 앱으로 실행. 다운로드 추가와 추가된 날짜순/이름순 선택, 등록 항목의 수동 순서를 제공함.
- R29: 휴지통은 **Finder에서 열기만 가능**. 선택 메뉴 대신 ‘휴지통은 Finder에서만 열 수 있습니다’ 안내를 표시. 기존 휴지통도 Finder 전용으로 전환하며 오버레이 조회·파일 열기·되돌려 놓기·외장 볼륨의 휴지통 수집을 구현하지 않음. R24/R25의 로컬 휴지통 오버레이 탐색을 대체함.
- R31: 휴지통 타일은 **Dock에서 여는 Finder 통합 휴지통**을 대상으로 함. `~/.Trash`나 특정 볼륨 폴더를 여는 것으로 대체하지 않음. Finder의 애플리케이션 `trash` 객체를 `NSWorkspace.OpenConfiguration.appleEvent`로 열며, 실패하면 오류를 알리고 로컬 폴더로 자동 대체하지 않음. 기존 휴지통 등록의 경로는 식별자 호환용으로만 유지함.
- R28: 로그인 시 자동 실행 토글을 제공. `SMAppService.mainApp`의 실제 등록/승인 상태를 표시하고 사용자가 끄면 해제. 시스템 설정에서 바꾼 상태도 앱 복귀 시 반영하며 시작할 때 재등록을 강제하지 않음.
- R38은 R28의 무조건 기존 앱 유지 정책을 대체함. 같은 버전·빌드는 새 실행을 종료하고 기존 앱을 유지. 다르면 기존 앱의 정상 종료를 확인한 뒤 나중에 실행한 앱을 사용하며 버전 숫자의 대소는 따지지 않음. 앱 복사본·직접 실행·동시 실행은 잠금으로 직렬화하고 실제 프로세스 시작 시각으로 나중 실행을 구별함. 거부/15초 시간 초과 시 강제 종료하거나 두 번째 앱을 시작하지 않음.
- 버전 비교 구현 기준: 표시 버전 + 빌드 번호 + 컴파일 결과 SHA-256. 실행 시점의 값을 PID/시작 시각과 함께 기록하여 같은 경로의 덮어쓰기나 PID 재사용을 구별함. 잠금 파일은 삭제하지 않음. 기록 없는 이전 개발 버전은 런타임 버전을 알 수 없으므로 정상 종료 후 교체. Finder 재열기가 기존 프로세스를 재사용하는 경우 디스크의 빌드를 확인하고 새 인스턴스로 교체 절차를 시작함.
- 앱별 고정 메뉴·메뉴 순서 편집·집중 모드 프로필 연동은 다음 단계. 메뉴 영역은 준비 상태를 표시하며 실행되는 것처럼 꾸미지 않음.
- 에이전트가 정한 초기 개발 기본값: 좌/우 Option 단독 250ms, 클릭으로 대상 지정 후 Option을 놓으면 실행. 표시 전의 타이핑·다른 보조키 조합은 호출 취소. 표시 후에는 R39의 단축키/보조키 유지 규칙을 적용하고, 고정하지 않은 창은 선택 없이 Option을 놓으면 닫음. 마우스만 올리거나 호출 순간 포인터 아래 항목이 생기는 것으로 실행하지 않음.
- 크기: 정상 범위 760–1,040pt × 620–720pt, 목표 비율 1.25, 허용 비율 1.2–1.5, 사용 가능 화면 안쪽 여백 24pt. 높이는 여백 제외 작업 영역의 80%를 출발점으로 제약을 함께 적용. 화면 면적 50%를 강제하지 않음. 기본값은 Apple 고정 지침이나 사용자 외관 최종 승인이 아님.
- 작은 작업 영역은 간격을 줄이고 최근 앱을 가로로 재배치하며 메뉴 준비 영역을 생략. 폰트를 통째로 축소하지 않음. 512×420pt 패널조차 수용하지 못하는 화면은 안내하고 메뉴 막대 설정은 계속 제공. 이 하한은 첫 빌드 제한으로 실제 UI 검증 대상임.
- 최근 창: 타일 최소 너비 148pt·간격 10pt·2줄, 최소 용량 6. 자동 수용량 또는 수동 6 이상 정수(제품 고정 상한 없음), 실제 창 수로 제한. 창이 적으면 실제 창만 표시. 최근 앱은 우선 3개.
- 현재 창 포함. 실행 중인 앱·열린 OS 창을 세션 단위로 추적하고, 닫힌 항목은 제거. 앱 시작 전에 관찰하지 못한 창의 과거 순위를 만들어내지 않으며 관찰된 항목 뒤에 둠. iTerm 탭·분할은 별도 창으로 간주하지 않음.
- 오버레이가 열린 동안 목록 순서·위치는 고정하고 재호출 시 최신 순서·스크롤 처음으로 복귀. 실제 동작 전 대상 유효성 확인. 권한 없는 경우 창 기능 안내와 등록 앱·폴더 기능을 제공.
- Swift Package + AppKit NSPanel + SwiftUI, NSGlassEffectView 사용. macOS 26+ 대상, 첫 빌드는 로컬 현재 아키텍처. Xcode 설치로 전역 개발 도구 선택을 임의 변경하지 않음.
- 요청·선택·초기 기본값은 문서에 기록. 컴파일·단위 테스트 통과와 실제 권한/입력/성능 검증 결과는 따로 보고함.

## 배경과 성공 기준

사용자는 Mac의 터치바를 편하게 사용했지만, Stream Deck은 손이 닿는 곳에 놓으면 책상 공간을 많이 차지한다고 느꼈습니다. 키보드에서 손을 크게 옮기지 않고 큰 패널을 불러내며, 앱·창·명령을 빠르게 선택하는 경험이 목표입니다.

참고 앱: [SwapBack App Store 페이지](https://apps.apple.com/kr/app/id6795126679). 사용자가 설명한 ‘Option을 누르면 선택기가 나타나는 동작’을 참고합니다. 해당 앱의 내부 구현은 확인하지 않았습니다.

## 사용자가 명시한 요구

### 호출과 조작

- macOS용 앱.
- Option을 누르고 있는 동안 선택 패널 표시.
- 마우스·트랙패드 중심으로 큰 항목을 클릭해 선택.
- 화면 면적의 약 절반을 차지하는 큰 오버레이. 초기의 ‘거의 전체 화면’ 표현보다 R16의 ‘면적의 반 정도, 100%는 아님’이라는 최신 설명을 우선함.
- 타일형 UX: 위치가 명확하고 클릭 영역이 크며, 여러 종류의 동작을 한눈에 찾을 수 있어야 함.

### 내용

- 최근 앱 목록.
- **모든 앱을 대상으로 하는 최근 창 목록.** macOS Command+`처럼 현재 앱의 창에만 한정하지 않음.
- 수동 등록 앱 목록. macOS 집중 모드에 따라 다른 구성을 표시.
- 현재 사용 중인 앱에 맞는 수동 등록 메뉴. 예: Excel의 이미지 용량 줄이기 명령.
- 최근 사용 메뉴는 수집이 충분히 신뢰할 수 있을 때만 추가. 어려우면 고정 메뉴만 있어도 됨.
- 우선 사용 비중: 최근 창·등록 앱·고정 메뉴가 높음. 최근 앱은 보조 기능.

### 최근 앱과 최근 창의 구분

- 최근 앱은 앱 단위로 중복 제거하되 최근 순서를 유지.
- 최근 창은 서로 다른 창을 각각 유지. 같은 앱의 창이 연속 또는 사이에 다른 앱을 끼고 등장할 수 있음.
- 앱마다 창이 하나뿐이면 두 목록의 앱 순서가 같아져도 정상. 두 영역을 합치거나 중복이라는 이유로 제거하지 않음.
- 아래 예시는 **왼쪽이 최신, 오른쪽이 과거**이며, 표시 상한이 앱 3개·창 3개라고 가정한 사용자 예시임.

| 최신 → 과거의 창 이력 | 최근 앱 | 최근 창 |
|---|---|---|
| iTerm cc2 → iTerm se3 → Safari 네이버 → Chrome Google | iTerm → Safari → Chrome | iTerm cc2 → iTerm se3 → Safari 네이버 |
| iTerm cc2 → Safari 네이버 → iTerm se3 → Chrome Google | iTerm → Safari → Chrome | iTerm cc2 → Safari 네이버 → iTerm se3 |
| iTerm cc2 → Safari 네이버 → Chrome Google | iTerm → Safari → Chrome | iTerm cc2 → Safari 네이버 → Chrome Google |

최근 창은 창 이름이 보여야 하므로 **최근 앱보다 넓은 공간과 더 많은 항목**을 제공합니다. 위의 3개는 정렬 설명용이며 실제 UI 개수 제한이 아닙니다.

### 최근 창의 표시 개수와 반응형 배치

- 최근 창은 **최소 6개를 담는 공간, 2줄 배치**를 기준으로 함.
- 화면의 사용 가능한 크기에 따라 오버레이 크기가 달라지고, 최근 창 영역도 이에 맞춰 조정됨.
- **자동 모드:** 최근 창 영역에 읽기 좋은 크기로 들어가는 개수를 계산. 큰 영역에서는 열을 늘려 더 많이 표시하며 6개·8개 같은 고정된 최대 개수는 두지 않음.
- **수동 모드:** 사용자가 최근 창 개수를 직접 지정할 수 있음. 최소 6개이며 제품 정책상 고정 상한을 두지 않음.
- 최대 개수 제한 없음은 한 화면에 무한히 배치한다는 뜻이 아님. 한 화면의 수용량은 가용 공간과 타일의 최소 크기에 의해 결정되며, 실제 표시 대상 창 수에도 한정됨.
- 실제 대상 창이 6개 미만인 경우에는 존재하는 창만 표시하고, 없는 창을 만들어 채우지 않는 것으로 해석함.
- 수동 지정 개수가 한 화면에 들어가지 않을 때의 탐색 방식은 아래 권장안을 따르되 아직 사용자 수락 전임.

### 최근 창의 정렬과 스크롤 방향 — 비교 요청

- 사용자가 두 안의 사용성 비교를 요청함: 행 우선 `1 2 3 / 4 5 6` + 세로 스크롤, 또는 열 우선 `1 3 5 / 2 4 6` + 가로 스크롤.
- 최신 항목들이 첫 화면에 연속으로 보여야 함. 전체 목록을 두 개의 긴 행으로 나누어 최신 4~6번째 항목이 오른쪽 밖으로 밀리는 배치는 피함.
- 에이전트의 최신 추천은 **행 우선 정렬 + 최근 창 영역 안의 세로 스크롤**. 이때 2줄은 한 번에 보이는 영역이며, 추가 행은 스크롤하여 접근함. 사용자가 어느 안을 선택한 것으로 확정하지 않음.
- 기존 R13의 가로 넘김 추천은 R15의 비교 검토와 최신 세로 스크롤 추천으로 대체됨. 가로 대안을 구현한다면 열 우선으로 채우며, 세로/가로 모두 처음에는 최신 1~6번째가 함께 보여야 함.
- 근거와 예시는 [조작 방식 검토](interaction-design.md)에 기록함.

### 오버레이 크기와 표시 위치

- 오버레이는 화면 면적의 약 절반. 가로와 세로를 각각 절반으로 만들어 면적이 1/4이 되는 것으로 잘못 해석하지 않음.
- R19: 현재 시안의 세로 길이는 괜찮으므로 유지하고 가로 폭을 더 줄여볼 것. 디스플레이 비율만 따르지 말고 오버레이의 최소·최대 크기도 제한할 것.
- R20: 오버레이 자체의 가로세로 비율에도 허용 범위를 두어 지나치게 가로로 길거나 좁아지지 않게 할 것. 32:9와 4:3 모니터에서도 패널의 형태와 사용감이 크게 달라지지 않아야 함. 디스플레이의 종횡비를 그대로 따라가는 방식은 사용하지 않음.
- 약 절반은 초기 크기 감각을 위한 목표이며, 가로를 줄인 만큼 세로를 늘려 면적 50%를 강제로 유지하지 않음. 구체적인 최소·최대 숫자는 아래 에이전트 검토안이며 아직 사용자 확정값이 아님.
- 사용자는 커서를 중심으로 오버레이를 여는 방식을 제안하고 편의성 검토를 요청함. 커서 중심 호출은 아직 최종 선택 전임.
- 위치 방식과 관계없이 **화면 밖으로 나가지 않아야 함**.
- 에이전트 추천: 호출 순간 커서가 있는 모니터에서 커서 중심으로 열되, 사용 가능 영역의 가장자리 여백 안에 들어오도록 위치를 보정. 열린 뒤에는 커서를 따라 이동하지 않음. 화면 중앙 고정은 선택 가능한 대안으로 제안함.
- 창 위치는 커서 기준이어도 메뉴의 대상 앱·창은 호출 직전 활성 앱·창을 유지함. 커서 아래에 있는 앱으로 문맥을 임의 변경하지 않음.

### 수락된 레이아웃 방향

- 상단: 현재 앱 이름·문맥, 적용 중인 프로필.
- 가운데 왼쪽: 현재 앱의 고정 메뉴, 필요하면 최근 실행 메뉴.
- 가운데 오른쪽: 집중 모드별 등록 앱.
- 하단 작은 영역: 최근 앱.
- 하단 큰 영역: 여러 앱의 최근 창, 창 제목 표시.
- 사용자는 최초 비교 시안의 세 번째 배치를 선호했고, 최근 앱을 줄이고 최근 창을 확대한 후 “레이아웃은 너무 마음에 든다”고 명시함.
- 후속 디자인 수정에서도 “레이아웃이나 UX는 마음에 든다”고 재확인함.

### 시각 디자인

- **macOS UI + 타일형 UX.** Windows 타일의 색상·각진 표면·박스 반복을 복제하는 것은 원하지 않음.
- Liquid Glass 적용 요청.
- 곡률·재질·아이콘·여백·강조 방식이 Apple의 실제 macOS 디자인과 자연스럽게 연결되어야 함.
- 직전 시안은 “애플 리퀴드 글래스 곡률이 아님”, “여전히 너무 윈도우 느낌”이라는 피드백을 받음.
- 시각 디자인은 미확정. 이후 수정본을 이미 승인된 디자인으로 취급하지 않음.
- 최신 피드백: 배경이 없어서인지 시안에서 Liquid Glass 느낌이 약함. 실제 네이티브 API를 사용했을 때 자연스러운 재질 표현이 가능한지 확인 요청. 웹 시안만으로 최종 재질을 평가하거나 디자인 승인으로 간주하지 않음.
- 앞으로 macOS가 바뀌면 당시의 Apple 지침을 확인하여 외관을 갱신할 수 있어야 함.

### 배포와 성능

- 우선 개인용으로 기능·사용감 검증.
- 기능을 제한해야 한다면 App Store에 올리지 않음. 기능 유지가 가능하면 App Store도 고려.
- 향후 Homebrew 배포 의향. GUI 앱이므로 Cask 경로를 검토.
- 아이콘·프리로드·창 전환 시 자원 사용에 대한 우려가 있음. 사용자는 최적화 방식의 선택을 개발자/에이전트에게 위임함.
- 사용자가 제시한 ‘열린 창의 메뉴를 전부 프리로드’는 아이디어이며 필수 구현 요구가 아님.
- 앞으로의 요청도 파일에 남길 것.

## 에이전트의 현재 권장안 — 확정 요구와 구별

- Swift/AppKit·SwiftUI 기반 네이티브 앱. 현재 SDK의 Liquid Glass 컴포넌트 활용.
- 처음에는 아이콘과 창 제목을 표시하고, 실시간 창 썸네일은 후속 검토.
- 아이콘·등록 항목·배치는 캐시. 앱·창 이력은 이벤트에 따라 갱신.
- 모든 창의 전체 메뉴를 계속 읽지 않음. 메뉴 경로·명칭과 실행 시점의 활성 상태를 구분하여 관리.
- 런처를 열 때 캐시로 먼저 표시하고, 필요한 조회는 UI를 막지 않는 작업에서 제한된 범위로 수행. 메뉴 실행 직전 대상 앱·창과 명령의 유효성 재확인.
- 메뉴 편집 시 현재 앱의 메뉴 목록에서 선택하여 고정 항목 추가.
- 시스템 전체의 최근 메뉴 추적보다 ‘이 런처에서 실행한 메뉴 이력’을 우선 검토.
- 집중 모드 필터로 macOS 집중 모드와 앱 내부 프로필 연결. 미설정 시 기본 프로필과 수동 선택 제공.
- Option 단독 누름 지연·조합키 충돌 처리. 메뉴에 보조키가 섞이지 않도록 실행 타이밍 검증.
- 최근 창의 과거 시안은 6개/8개 선택만 제공했음. 이후 R13의 최소 6개·2줄·자동/수동·고정 상한 없음 요구가 이를 대체함. 최근 앱 3개는 여전히 시안 값이며 확정 규격이 아님.
- 패널 크기는 표시할 모니터의 현재 사용 가능 영역을 포인트 단위로 읽고 계산. 물리적 해상도만으로 타일을 늘리지 않음. 메뉴 막대·Dock·화면 배율·안전 영역 및 전체 레이아웃의 높이를 고려함.
- 자동 배치의 계산안: 최근 창 영역의 안쪽 너비를 W, 읽기 좋은 최소 타일 너비를 m, 간격을 g라 하면 열 수는 floor((W + g) / (m + g)), 수용량은 열 수 × 2. 지원할 화면에서 최소 3열이 들어가도록 전체 패널 폭과 영역 비율을 확보함. 3열도 들어가지 않는 예외 환경에서는 화면 밖으로 넘기거나 읽을 수 없게 축소하지 않고 2줄 탐색으로 전환하는 방안을 검증함. m과 g는 실제 제목·접근성 설정으로 검증하며 아직 숫자를 고정하지 않음.
- 수동 모드의 개수는 최근 창 목록에 포함할 목표 수로 해석하는 안을 제안함. 한 화면에 들어가면 최대 2줄에 배치하고, 넘치면 타일 최소 크기를 유지하며 세로로 스크롤. 열 수는 전체 지정 개수가 아닌 실제 표시 영역의 너비로 정하고, 왼쪽부터 행 우선으로 채움. 마지막 행의 남는 칸은 비우며 실제 창 수가 지정값보다 적으면 실제 창만 표시함. 가로 대안과의 최종 선택은 미확정.
- 자동 모드는 기본적으로 한 화면에 들어가는 최근 창을 표시하고, 수동 모드는 지정한 창까지 탐색 가능하게 하는 방향. 매우 큰 수를 입력해도 실제 창 수까지만 사용하고, 화면에 보이는 항목 위주로 뷰를 생성하여 지정값에 비례해 메모리를 미리 할당하지 않음. 무제한 이력 보관을 요구한 것으로 해석하지 않음.
- 크기·배율 변경이나 다른 모니터에서의 호출 시 수용량을 다시 계산. 일반적인 창 전환만으로 타일 폭·순서를 흔들지 않으며, 패널이 열린 동안에는 선택 위치가 바뀌지 않도록 함. 닫았다가 다시 열면 최근 창 목록의 시작 위치부터 표시하는 안을 제안함.
- 세로 스크롤은 최근 창 영역에만 적용하고 상단·고정 메뉴·등록 앱·최근 앱은 고정. 작은 스크롤 표시 등으로 더 많은 항목의 존재를 알리고, 일반 마우스와 트랙패드 모두 검증. 방향을 사용 중 자동으로 바꾸지 않음.
- 커서 중심 배치의 크기는 모니터의 사용 가능 영역으로 계산한 뒤 중심 좌표를 보정. 가장자리 근처에서도 같은 모니터에서는 패널 크기와 내부 순서를 유지하고 위치만 이동함. 화면 면적의 약 절반은 목표값으로 두고 최소 6개와 제목 가독성, 화면 안에 들어오는 제약을 함께 검증함.
- 크기 검토안: 가로 760–1,040pt, 세로 620–720pt를 후보 범위로 유지하되, 폭과 높이를 독립적으로 결정하지 않고 R20의 패널 비율 조건과 함께 계산. R19의 ‘화면 너비 약 65%’를 출발점으로 삼는 안은 패널 자체의 비율·기준 크기를 우선하는 안으로 대체함. 높이를 면적 50%에 맞춰 키우지 않으며 이 수치는 Apple의 고정 지침이나 구현 완료 값이 아님.
- 패널 비율의 초기 검토값은 가로:세로 5:4(1.25:1)를 중심으로 1.2:1–1.5:1 범위. 사용자가 확정한 값은 아니며 현재 좁힌 시안과 실제 콘텐츠를 기준으로 조정. 기준 크기가 들어가는 화면에서는 형태와 높이감을 유지하고, 32:9의 추가 가로 공간은 주로 여백으로 남김. 4:3에서도 가능한 한 같은 형태를 유지함.
- 비율·최소/최대 크기·화면 경계를 동시에 만족하는 크기를 선택. 가용 공간이 작으면 최소 크기를 기계적으로 강제하지 않고 비율을 유지하는 크기를 먼저 검토하되, 글자·아이콘을 통째로 축소하지 않음. 최소 6개와 가독성을 함께 만족하지 못하는 환경은 별도의 작은 화면 대응으로 명시하여 검증함.
- 화면 가장자리 여백을 뺀 가용 크기가 제안 최소값보다 작으면 화면 내 배치를 우선하고 작은 화면 대응을 따로 검증. 오버레이 크기에 상한이 생겨도 최근 창 목록의 수동 개수에 고정 상한을 추가하지 않음.
- 최신 계획용 시안은 가로 목표 800 CSS px로 축소하고 760–1,040px 비교 조절을 추가함. 메뉴 타일 높이·세로 간격·레이아웃 구성은 유지. 이 웹 미리보기의 CSS px를 macOS 포인트 단위의 검증 결과로 간주하지 않음.
- 오버레이가 열린 순간 커서 밑에 항목이 생겼다는 이유만으로 선택·실행하지 않음. 포인터를 강제로 이동시키지 않으며, 실제 클릭 또는 명시적인 선택을 통해 실행하도록 입력 동작과 함께 검증함.
- 실제 재질은 AppKit의 NSGlassEffectView 또는 SwiftUI의 glassEffect 등 지원 OS의 공식 API로 검증. 배경·재질 변형·배치·곡률·접근성 설정을 함께 조정하며 API 적용만으로 특정 시스템 패널과 동일한 외관을 보장하지 않음. 웹 시안의 불투명도 55%를 네이티브 재질의 필수 규격으로 옮기지 않음.
- 최근 정렬은 마지막 사용·전환 시각으로 해석. 시안은 현재 창을 포함하고, 실제 패널이 열린 동안에는 순서를 고정하는 방향을 제안함.
- 핀으로 패널 유지, 직전 명령 재실행, 폴더·URL·단축어 타일, 설정 백업은 추가 제안이며 첫 버전에 포함하기로 확정하지 않음.

## 구현 전에 확인하거나 검증할 사항

- 지원할 최소 macOS 버전, 정식 제품명, 첫 버전의 최종 범위.
- Option 좌/우 선택, 지연 시간, 클릭 후 실행 시점, 별도 호출 단축키.
- 현재 창 포함 여부, 닫힌 창·종료 앱의 이력 취급. 최근 창의 최소 6개·2줄·자동/수동 모드는 확정 요구이며, 타일 최소 너비와 수동 모드 초과 항목 탐색 방식은 검증/미확정 사항.
- iTerm의 cc2/se3가 별도 OS 창인지, 같은 창의 탭·분할 세션인지. 현재 예시 구현은 별도 창을 가정하며 탭·분할은 별도 연동 영역.
